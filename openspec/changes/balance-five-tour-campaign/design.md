# Design

## Context
See proposal.md for motivation. The current Dart model has four species, multi-hit elites, bounded repeat scaling, three lives and no completion state. CampaignStory shares five arrival/victory captions; SectorBackground combines five PNG worlds with procedurally painted stars and occupation scenery. Main owns title, HUD, cinematics and score rows. Scores currently contain only initials/score; the worker strictly rejects additional keys and prunes one global SQLite table to ten entries. Existing tests include endless-run, progression, cinematic, background, controls and score behavior.

## Goals / Non-Goals
**Goals:** Centralize difficulty/route tuning; retain deterministic model tests; make checkpoints independent of rendering internals; migrate existing scores without deletion.

**Non-Goals:** Exact mid-frame restoration, account synchronization, replacing ordinary enemy artwork, and production deployment in this change.

## Decisions

### Difficulty policy
Use an explicit difficulty enum separate from the existing RunMode phase enum. Policy owns starting lives, enemy speed/cadence, roster budgets, scoring and pickup probability. Easy scales hostile movement and firing rate to 0.9 while retaining player speed/fire; boss health is round(normal ×0.8). Normal/Hard retain current boss hit totals. Easy enemy points are ×0.75, Normal/Hard ×1. Reduce the initial heart-drop defaults of 4%/3%/0% substantially: those rates produce too many pieces as roster sizes grow. Use 1.2% Easy / 0.8% Normal / 0% Hard per eligible kill, retain independent power drops, and verify expected pieces across complete early and dense late routes rather than evaluating one kill in isolation.

Preserve current Normal base rosters. Easy uses approximately 80%, Hard 120%, rounded with a minimum roster. Later-route extra roster growth is +1/+3/+4 enemies per route in Easy/Normal/Hard, with bounded counts and spacing. Raise the present 24-enemy ceiling only alongside layout and bullet-budget validation. Hard remains the strict life economy; greater density supplies its extra challenge. Avoid speeding all simulation time: that would also impair the player and distort elapsed time.

### Small checkpoints and separate history
Use browser local storage through a platform abstraction with a test/in-memory implementation and safe native fallback. It can hold compact JSON without sending state with HTTP requests as cookies would. Write once on each wave/boss entrance, not every frame or unload. Also clear on game over/completion and replace on a new run. Persist history only on failure or unlock events. Returning to title keeps the latest checkpoint.

Checkpoint fields: schemaVersion, difficulty, route index, sector, wave, score, lives, medals, kills, heart slots and activeMilliseconds. No positions, entities, power timers or random engine state. Restart the wave from its normal entrance; clear powers. Restore accumulated time from that same boundary, intentionally replaying any unsaved wave time and score. Validate known values; default missing optional fields, tolerate additional fields and preserve valid old route identifiers through mappings if names change. Do not reject merely because an optional version field differs. Malformed required route data disables Resume without blocking Start. A schema-less minimal checkpoint defaults to Normal, first route/sector, mode starting lives, zero medals/hearts/time and known score/wave. Schema 2 checkpoints include `heartParts: 4`; without that marker, map the old lower-left/lower-right bits unchanged and old top bit 4 to both new top bits (12), preserving earned progress.

Three failures before any boss victory unlock Easy permanently. Any boss victory records everBeatBoss; only Normal victory unlocks Hard, and unlocking Hard also unlocks Easy. Resuming does not count as failure. History is separate so replaying a checkpoint cannot revoke earned unlocks.

### Rewards and finite progression
Keep internal route indices 0–4 while presenting names. Award medal count and +1UP once in the boss-defeat transition, then animate wreck, recognition and route departure. The next wave checkpoint includes committed rewards; interruption during reward presentation replays the preceding wave rather than stacking rewards. A distinct completed phase ends route five and captures remaining lives after +1UP for score submission. Count time in active combat updates only. Pauses, salvage, introductions and travel do not count.

Heart inventory is three sets of four quarter bits: bottom-left=1, bottom-right=2, top-left=4, top-right=8; full mask=15. Fill the first set missing a picked part; when complete, increment lives and clear that set. Three identical quarters occupy three sets; a fourth is ignored. Paint four complementary quarters of one heart outline, with clear bottom-left/bottom-right/top-left/top-right identity and recognizable unfilled regions. Keep a short completed-heart and explicit +1UP cue independent of the cleared slot so the player can connect completion to the added life. Life HUD uses a count when icons cannot fit rather than truncating at three.

### Enemy and boss presentation
Add separate enemy archetype identity from existing species and damage stages so ordinary sprites keep their forms. Initial rare archetypes: a wide shielded line-wing sentinel and a heavier armored variant for later Normal/Hard waves. Require at least one defeated boss in the current run; saved device unlocks alone never permit first-route spawns. Select eligible final-wave refreshes initially; stronger modes gain later-wave eligibility only after this gate. Introduce a small ordinary swarm first, then slowly bring the sentinel down from above the arena to a hover row above every ordinary enemy. Make the hover prolonged, wing motion a very slow sequence of segmented poses, and the eventual dive fast and heavy after a creature-associated pixel warning. Keep return/hover/dive state distinct from ordinary enemy motion so a generic immediate dive cannot skip the presentation. Bound simultaneous large threats, starting at one. Use a unique pixel-frame wing breakup/falling-ember defeat sequence. Keep score/drop awards single-shot through the normal kill path.

Treat the Atari-era reference as a silhouette, palette and stepped-animation direction, never source art to copy. Author the sentinel, armor, warnings and carrier smoke/flames as original low-resolution pixel frames using a small explicit palette; sample nearest-neighbor and preserve square logical pixels when enlarged. A deterministic generator is appropriate, but painting smooth runtime vector birds, arrow warnings or continuously deforming flame paths is not. Keep this rule in the main `arcade-presentation` spec and production style guides so future additions follow it.

Give a minority of sentinels a one-time eligibility selection for a rare sacrifice rush, available at health ≤25%; do not reroll eligibility each update. At commitment, sample the player's position once and show a subtle distinct pose on the creature itself plus a small preparatory movement for 0.9 seconds. Then launch at 600 arena units/second (540 in Easy) on a fixed straight trajectory toward that sampled position: movement after the tell must allow a dodge, without homing or later retargeting. Once committed, the sentinel cannot resume its normal loop; impact or leaving the arena destroys it without score, kill count or drops. Keep it shootable throughout the tell and rush, with the normal single award if player fire destroys it first. Distinguish the last-stand tell from an ordinary dive using silhouette and movement as well as color; all effects retain stepped pixel frames.

Use one local centerline for boss belly, shield and hatch geometry so viewport scaling cannot introduce asymmetry. Shield health controls visible width/coverage; keep enough visible outline to distinguish active from broken. Core health drives smoke/sparks/flames. Preserve door timing/collision semantics and remove both bar/text health meters. Capture a wreck visual on death so removing the live boss does not erase the falling animation.

Each ordinary wave may schedule finite reinforcement groups: 0–2 in Easy, 0–3 in Normal and 1–4 in Hard according to route/sector, each 4–6 demons and at most 42 active enemies. A fresh small escort group precedes a delayed sentinel entrance. Reinforcements do not create wave checkpoints. Sentinels can evade incoming fire, carry separately depleted shield/armor before hull health, and fire distinct faster bullets. Their eight articulated wing poses hold 0.4 seconds each (3.2-second cycle), with separate ordinary warning/falcon-dive and last-stand poses. Carrier movement starts with seeded random direction/phase and accelerates with damage; pixel rage eyes reinforce that escalation. Lower explosion opacity and improve stepped smoke while preserving projectile readability.

### Extended temporary powers
Add `Power.powerful` and `Power.large`. Powerful and Rapid replace each other; Large and Spread replace each other; Shield remains independent. All active effects retain independent nine-second timers, per-type refresh, and existing pause behavior. Powerful deals double damage at normal fire cadence with a distinct shot. Large creates a small pixel impact blast damaging nearby demons; splash can reach a carrier core only after shield depletion while its door is open. Powerful, Large and Shield may combine. Cycle guaranteed power drops every eight player kills through Spread, Rapid, Shield, Powerful, Large; sacrifice self-destruction never advances that cycle. Use cyan side cannons, gold central bolt, red central heavy cannon, amber side explosive shells and violet outer shield as transparent glyph layers; retain RAPID label for existing fast-fire behavior.

### Story and layered worlds
Use a 5×5 route table shared by HUD, arrivals, travel and backgrounds. Proposed sector variants, ordered by route:
- Krybor; Krybor Slums; Krybor Docks; Krybor Mountains; Krybor Command.
- Ringfall; Ringfall Patrol Belt; Ringfall Wreckfields; Ringfall Shipyards; Ringfall Blockade.
- Ember Moon; Ember Ashlands; Ember Forges; Ember Crucible; Ember Brood Heart.
- The Hollow; Hollow Outskirts; Hollow Towers; Hollow Catacombs; Hollow Throne.
- The Carrier; Brood Ark; Siege Carrier; Brood Citadel; Brood Flagship.

Retain existing world themes and original artwork. Add independently scrolling pixel-grid terrain, silhouettes, orbital structures and occupation layers with distinct depth rates and route-specific composition. Names must correspond to visible places: Krybor Slums needs dense irregular habitation, Docks needs docking gantries/berths/cargo structures, Mountains needs stepped peaks and ridges, and Command needs organized fortified structures. Apply equivalent silhouette distinctions to every sector's variants; increasing generic tower count or changing tint alone is insufficient. Later routes reveal more layers without obscuring projectiles. Caption writing connects the exact previous and next destinations and culminates at the base. Recognition uses fleet service language and an animated medal plus heart. Enlarge responsive story text beyond the initial campaign implementation and give text-bearing phases about one third of a second more reading time (4-second clear/travel becomes approximately 4.33 seconds). Larger text panels and travel bars use arena space; verify the longest complete captions on narrow phones and landscape without clipping. Redraw the spread layer as twin cannon barrels with broad muzzle openings and angled weapon mounts, legible on its own and within the shield. Keep power status over the controller using an overlay/fixed guidance anchor, rather than allowing its width to change label placement.

### Illustrated first-wave hints
Replace repeated first-wave arrival story captions with a contextual shuffled hint, one five-to-nine-word action sentence and one original pixel illustration. Keep destination identity visible and leave travel/recognition storytelling intact. Choose once per entrance from eligible hints, excluding hearts in Hard and sentinel advice before a current-run boss victory; avoid repeats until the eligible bag is exhausted and avoid immediate repeats across bags when possible. Pause/rebuild must not redraw the selection.

Use a 4.5-second default instead of the former approximately 2.633-second first-wave introduction, with the full card visible throughout. Hold/Pause freezes the card and clock; Resume continues the same remaining interval. Add an untimed Field Guide on landing and pause, with the same content and optional fuller explanations; closing it does not resume gameplay. Persist an automatic-advance preference in run history; disabling it holds each briefing until explicit Continue. This default and the five-to-nine-word budget are tuning decisions, not published universal reading thresholds. Primary-source rationale and review guidance are in `plan/hint-usability.md` (Microsoft XAGs, W3C timing guidance and Apple HIG). Treat artwork as a concise explanation of the action, not a decorative title illustration.

Shield advice must reflect the actual cause: a shield absorbing a hit grants one second of invulnerability and consumes that shield; collecting a new shield during that grace restores its nine-second timer. Expiring without a hit grants no grace. Preserve this distinction in the short line, illustration, untimed explanation and behavioral checks.

### Scores and compatibility
Extend ScoreEntry and the worker payload with difficulty, medals, activeMilliseconds and remainingLives. Missing mode defaults to Normal; legacy rows use zero medals/time and no finisher lives. Display unknown legacy time as an em dash rather than implying a measured zero. Add SQLite columns with migration guards; preserve the current Durable Object identity so its scores survive. Filter and prune per mode, maintaining score-descending/id-ascending ties. Extend payload size limit deliberately and validate integer ranges and completion consistency before writes. Only include finisher lives for five-medal results. UI hides locked boards; this is a local progression feature, not authorization against direct endpoint access. Keep failed submission metadata immutable for retry.

## Risks / Trade-offs
- Wave replay can restore lost lives/score from its beginning → accepted checkpoint semantics; label Resume as restarting the saved wave.
- Browser data can be cleared or edited → unlocks are device-local and client scores remain trust-based, matching the current system.
- Roster growth can create excessive pressure → deterministic budget tests and playtest all five routes, especially Normal bosses and large-enemy overlap.
- Larger captions and score metadata crowd phones → responsive wrapping and browser verification at narrow/landscape sizes.
- Existing endless-run tests/specs conflict with a five-boss ending → replace the endless expectation while retaining regression coverage for prior phases and powers.

## Migration Plan
Implement additive worker schema/API compatibility before the extended client; retain old request support. Verify migration against a populated pre-change database and independent per-mode pruning. Validate local checkpoints with omitted/new fields. Complete model/widget/worker checks, then review managed Wrangler on phone and desktop. Do not deploy or merge as part of planning. For rollback, retain added columns and old scores; an older client can still submit legacy Normal payloads.
