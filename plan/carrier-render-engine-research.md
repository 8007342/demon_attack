# Research: the carrier rendering engine (C3, `carrier-render-engine`)

This research backs C3: one rendering engine for the carrier that (1) bends the ship as one rigid giant instead of
warping each of its ~15 module layers separately, (2) collapses it as connected structure instead of loose random
sprites, and (3) makes the force field visibly wear down instead of narrowing inward.

Provenance follows the project's CLAUDE.md §8. Every row carries its source:

## 1. Deforming the carrier as one body (D)

| ID | Conclusion | Source |
| --- | --- | --- |
| D1 | **Compose once, then warp once.** Record all module layers into one `Picture`, then call `toImageSync`. Where a GPU context exists, the image stays on the GPU and can be drawn as a texture without a read-back. | [source: Flutter, "Picture.toImageSync", https://api.flutter.dev/flutter/dart-ui/Picture/toImageSync.html, read 2026-11-16] — "If a GPU context is available, this image will be created as GPU resident and not copied back to the host." Also: "The image object is created and returned synchronously, but is rasterized asynchronously." |
| D2 | **The composite must cover the whole hull, including the parts off-screen.** `toImage` clips to its rectangle, so a composite sized to the arena would cut the hull. The rectangle must span the hull's full ~800×700 extent in the art's own space, not in screen space. See also X11. | [source: Flutter, "Picture.toImage", https://api.flutter.dev/flutter/dart-ui/Picture/toImage.html, read 2026-11-16] — "The picture is rasterized within the 0 (left), 0 (top), `width` (right), `height` (bottom) bounds." / "Content outside these bounds is clipped." |
| D3 | **Warp the composite with one textured triangle mesh:** `Canvas.drawVertices`, with `Paint.shader = ImageShader(composite, …)`. | [source: Flutter, "Canvas.drawVertices", https://api.flutter.dev/flutter/dart-ui/Canvas/drawVertices.html, read 2026-11-16] — "Image shaders can be used to draw images on a triangular mesh"; "The Paint.shader property, if set, overrides the color entirely". |
| D4 | **Build the mesh with `Vertices.raw` and an index buffer.** Then neighbouring triangles reference the *same* vertex, and a single displaced vertex moves every triangle that uses it. Per-layer warps give each layer its own copy of an edge, and those copies drift apart (the operator's "layers drift apart"). One indexed grid has no such duplicate edges, so it cannot open a seam. | [source: Flutter, "Vertices.raw", https://api.flutter.dev/flutter/dart-ui/Vertices/Vertices.raw.html, read 2026-11-16] — `textureCoordinates` "must be the same length as `positions`"; indices "must have at least three entries"; indices may reuse points. The no-seam argument is ours: [UNSOURCED: plan/provenance-audit.md#CRE-1] |
| D5 | Use `VertexMode.triangles` with indices for a general grid. `triangleStrip` saves indices for each grid row. | [source: Flutter, "VertexMode", https://api.flutter.dev/flutter/dart-ui/VertexMode.html, read 2026-11-16] — triangles: "Draw each sequence of three points as the vertices of a triangle."; triangleStrip: "Draw each sliding window of three points as the vertices of a triangle." |
| D6 | **Sample the warped composite with `FilterQuality.low` (bilinear) or `.medium` (mipmapped).** Use `.medium` if the composite is drawn below half its size. Avoid `.none`: nearest-neighbour sampling shimmers under a slowly changing warp. Avoid `.high`: it is the slowest and is weaker when the scale is animated. | [source: Flutter, "FilterQuality", https://api.flutter.dev/flutter/dart-ui/FilterQuality.html, read 2026-11-16] — low: "a "Bilinear" algorithm which smoothly interpolates between pixels"; medium: "The best all around filtering method that is only worse than high at extremely large scale factors." |
| D7 | Set `filterQuality` explicitly on the `ImageShader`. Otherwise it is inherited from the paint and environment. | [source: Flutter, "ImageShader constructor", https://api.flutter.dev/flutter/dart-ui/ImageShader/ImageShader.html, read 2026-11-16] — "If `filterQuality` is not specified at construction time it will be deduced from the environment where it is used," |
| D8 | **`drawVertices` edges are not anti-aliased.** Give the composite a transparent margin of a few pixels and let the mesh boundary run through that margin, not along the hull silhouette. The silhouette then comes from the texture's alpha, which is filtered, instead of from the jagged triangle edge. | [source: flutter/flutter#77485, "Canvas.drawVertices does not use anti-aliasing", https://api.github.com/repos/flutter/flutter/issues/77485, read 2026-11-16] — "The drawVertices method does not use any anti-aliasing, even when it is enabled in the Paint settings." (open, filed 2021-03-06) |
| D9 | On native Impeller, `drawVertices` with texture coordinates costs an extra render-to-texture each draw. Keep the grid coarse and draw the carrier once per frame, not once per layer. This is one more reason to draw one mesh instead of 15. | [source: flutter/flutter#153045, "[Impeller] Improve mesh gradient performance by removing render to texture for drawVertices w/ texture coordinates.", https://api.github.com/repos/flutter/flutter/issues/153045, read 2026-11-16] — "To implement drawVertices w/ texture coordinates, Impeller will first render to texture and then re-sample the contents." (open) |
| D10 | Tint and flash the hull (damage, heat glow) with **vertex colours and a blend mode**, not a `ColorFilter`. One open Impeller issue reports that `drawVertices` with an image shader ignores the paint's colour filter. | [source: flutter/flutter#193893 (title only, from issue search), https://api.github.com/search/issues?q=repo:flutter/flutter+drawVertices+in:title, read 2026-11-16] — "[Impeller] `Canvas.drawVertices` with an image shader ignores the paint's colour filter". Blend semantics: [source: Flutter, "Canvas.drawVertices", https://api.flutter.dev/flutter/dart-ui/Canvas/drawVertices.html, read 2026-11-16] — "the colors from the paint parameter are considered the source," "the colors from the vertices are considered the destination." |
| D11 | **No vertex shaders in Flutter.** A geometric warp must therefore be done on the CPU, by moving `Vertices` positions each frame. A fragment shader can only displace UVs inside a fixed quad. The CPU mesh is the right tool for a bend that moves the silhouette. | [source: Flutter, "Writing and using fragment shaders", https://docs.flutter.dev/ui/design/graphics/fragment-shaders, read 2026-11-16] — "(Flutter doesn't support vertex shaders, which would have the `.vert` extension.)" |
| D12 | **Engine precedent for compose-then-treat-as-one:** Godot's `CanvasGroup` draws its children as one object. Overlapping translucent parts therefore do not double up, and a shader applies to the group as a whole. It needs a margin to avoid edge artefacts, which matches D8. | [source: Godot Engine, "CanvasGroup" class reference, https://raw.githubusercontent.com/godotengine/godot/master/doc/classes/CanvasGroup.xml, read 2026-11-16] — "Child [CanvasItem] nodes of a [CanvasGroup] are drawn as a single object."; clear_margin "should be increased if artifacts appear along the edges of the canvas group." |
| D13 | **Skeletal meshes deform one shared vertex set with weights.** Spine computes each world vertex as a weight-blended sum of bone transforms, plus optional per-vertex deform offsets. For the carrier, two or three "bones" (bow, midship, stern) can drive one hull grid with smooth weights. A slight turn then bends the hull continuously instead of rotating parts separately. | [source: Esoteric Software, spine-runtimes `VertexAttachment.cs` (4.2), https://raw.githubusercontent.com/EsotericSoftware/spine-runtimes/4.2/spine-csharp/src/Attachments/VertexAttachment.cs, read 2026-11-16] — "wx += (vx * bone.a + vy * bone.b + bone.worldX) * weight;"; "If the slot's <see cref="Slot.Deform"/> is not empty, it is used to deform the vertices." |
| D14 | **A bending mesh needs interior vertices.** With only boundary vertices, the triangulation folds unpredictably when it bends. Use a regular interior grid. A 12×10 cell grid is our starting guess for an 800×700 hull. | [source: Godot docs, "2D skeletons" (source rst), https://raw.githubusercontent.com/godotengine/godot-docs/master/tutorials/animation/2d_skeletons.rst, read 2026-11-16] — "Trying to animate bones that bend the polygon will often yield unexpected results"; "If the same point is painted white for multiple bones, the influence will be distributed amongst them." Also [source: Godot Engine, "Polygon2D", https://raw.githubusercontent.com/godotengine/godot/master/doc/classes/Polygon2D.xml, read 2026-11-16] — "Number of internal vertices, used for UV mapping." Grid size: [UNSOURCED: plan/provenance-audit.md#CRE-2] |
| D15 | **Free-form deformation (FFD):** embed the object in a lattice of control points and move the control points. The object follows smoothly, through Bernstein-polynomial interpolation. A 3×3 or 4×3 control lattice that drives the hull grid's vertices gives a smooth, global "turn" with few parameters. | [source: Sederberg & Parry, "Free-form deformation of solid geometric models", SIGGRAPH 1986, https://history.siggraph.org/?p=116034, unread: snippet only]. The PDF (people.engr.tamu.edu), the ACM page and Blender's lattice-modifier docs were all refused. **Not sourced.** |
| D16 | Live2D "warp deformers": a parameter-driven lattice that deforms all child art together, used for head and body turns. This would be the closest art-tool analogue to a parameter-driven carrier "turn". | [source: Live2D, "Warp Deformer", https://docs.live2d.com/en/cubism-editor-manual/warp-deformer/, unread: fetch refused]. **Not sourced.** |
| D17 | **Large size reads through duration.** Material's motion guidance scales duration with the area and distance an animation covers. A hull-sized deformation should therefore be slow: seconds, not a few hundred milliseconds. | [source: Google, material-components-android "Motion" docs, https://raw.githubusercontent.com/material-components/material-components-android/master/docs/theming/Motion.md, read 2026-11-16] — "In general, duration should increase as the area/traversal of an animation increases." / "Easing is a curve which determines how long it takes an object to start and stop moving." |
| D18 | Heavy objects move slowly, ease in and out, and their follow-through keeps moving after the main motion stops. Rigid, heavy objects show little squash. Applied to the carrier: the bend eases, lags the turn slightly, and settles. It never wobbles like rubber. | [source: Univ. of Washington CSE457, "Animation principles" lecture, https://courses.cs.washington.edu/courses/cse457/03sp/lectures/animation-principles.pdf, unread: snippet only (fetch refused)] — snippet: "Timing also reflects the weight of an object". [source: Lasseter, "Principles of Traditional Animation Applied to 3D Computer Animation", SIGGRAPH 1987, https://www.evl.uic.edu/aej/527/papers/lasseter.pdf, unread: fetch refused]. **Not sourced.** |
| D19 | For film-scale ships, directors asked for slower motion because fast motion looked physically unreal. | [source: vfxblog, "Ten things I learned from ILM about 'The Last Jedi's' space battles", https://vfxblog.com/2018/01/05/ten-things-i-learned-from-ilm-about-the-last-jedis-space-battles, unread: snippet only (fetch refused)]. **Not sourced.** |
| D20 | **Keep the bend small. A large swing is also an accessibility risk:** panning or scaling large objects is a known vestibular trigger, and a near-screen-sized hull is exactly such an object. Honour a reduced-motion setting by freezing the bend. | [source: MDN, "prefers-reduced-motion", https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion, read 2026-11-16] — "Animations such as scaling or panning large objects can be vestibular motion triggers." Our numbers (e.g. ≤1.5° equivalent shear, ≥3 s per cycle): [UNSOURCED: plan/provenance-audit.md#CRE-3] |
| D21 | Wrap the carrier painter in a `RepaintBoundary`, so HUD and bullet repaints do not re-record it. Our own composite cache (D1) is still needed, because the engine's raster cache is a hint and not a guarantee. | [source: Flutter, "RepaintBoundary class", https://api.flutter.dev/flutter/widgets/RepaintBoundary-class.html, read 2026-11-16] — "A widget that creates a separate display list for its child."; the engine "may choose to pay a one time cost of rasterizing and caching the pixel values of the subtree." |

## 2. Destruction (X)

| ID | Conclusion | Source |
| --- | --- | --- |
| X1 | **Pieces inherit the parent's motion: `v_piece = v + ω × r`.** Here r runs from the parent's centre of mass to the piece's centre. In 2D, ω × r = (−ω·r_y, ω·r_x). This is the formula physics engines use for the velocity of a point on a rigid body. | [source: Erin Catto, Box2D v2.4.1 `b2_body.h`, https://raw.githubusercontent.com/erincatto/box2d/v2.4.1/include/box2d/b2_body.h, read 2026-11-16] — "/// Get the world linear velocity of a world point attached to this body."; "return m_linearVelocity + b2Cross(m_angularVelocity, worldPoint - m_sweep.c);" |
| X2 | The same formula appears in Bullet. | [source: Bullet Physics, `btRigidBody.h`, https://raw.githubusercontent.com/bulletphysics/bullet3/master/src/BulletDynamics/Dynamics/btRigidBody.h, read 2026-11-16] — "return m_linearVelocity + m_angularVelocity.cross(rel_pos);" |
| X3 | **Fracture as broken connections:** Bullet's fracture demo stores connections between the parts of a compound body. Contact impulses wear each connection's strength down, and the parts that become disconnected become new bodies that copy the parent's velocity. Two things follow for the carrier. Model it as a connection graph between modules, so a break happens where damage has accumulated. And give each broken chunk the parent's motion (X1 is the exact per-point form; Bullet copies the centre-of-mass values). | [source: Bullet Physics, FractureDemo `btFractureDynamicsWorld.cpp`, https://raw.githubusercontent.com/bulletphysics/bullet3/master/examples/FractureDemo/btFractureDynamicsWorld.cpp, read 2026-11-16] — "connection.m_strength -= pt.m_appliedImpulse;"; "newBody->setLinearVelocity(fracObj->getLinearVelocity());"; "newBody->setAngularVelocity(fracObj->getAngularVelocity());" |
| X4 | A radial blast impulse applied to the chunks near a detonation adds a localized kick on top of the inherited motion. Box2D v3 provides this as a built-in. | [source: Erin Catto, Box2D `docs/simulation.md`, https://raw.githubusercontent.com/erincatto/box2d/main/docs/simulation.md, read 2026-11-16] — "`b2World_Explode()` efficiently applies an explosion in a circular area and also uses the shape's projected area." |
| X5 | **Voronoi shatter:** scatter seed points, biased toward the impact. Each seed owns one cell, and each fragment is the object clipped to its cell. For a 2D sprite: clip the *composited* hull texture's mesh to cells, and keep each cell's UVs into the same composite. Fragments then show the real art and match up exactly before they separate. | [source: J. Lucas, "Real-Time Brittle Fracture", https://jclucas.github.io/shatter/info.html, read 2026-11-16] — "each seed point corresponds to one subdivision, called a Voronoi cell."; "Each fragment is created by clipping the original object against each halfplane defining a Voronoi cell"; seeds sit in a circle whose "center … is halfway between the impact point and the center of the object". |
| X6 | **Pre-compute fractures. Do not cut at runtime on mobile web.** A 2D polygon-fracture library (Godot) offers Delaunay triangle fracture and random cut lines, and its author warns about the cost. | [source: SoloByte, "godot-polygon2d-fracture" README, https://github.com/SoloByte/godot-polygon2d-fracture, read 2026-11-16] — "Delaunay Fracture -> uses the delaunay triangulation to calculate random triangles inside the polygon."; "not the best or most performant method out there." |
| X7 | **Games pre-fracture and author multi-level hierarchies:** big chunks first, which can break again into smaller ones. | [source: Müller, Chentanez & Kim, "Real Time Dynamic Fracture with Volumetric Approximate Convex Decompositions", SIGGRAPH 2013, https://matthias-research.github.io/pages/publications/fractureSG2013.pdf, unread: the index page https://matthias-research.github.io/pages/publications/publications.html was read and lists the title, but the PDF exceeded the fetch size limit; the claim is snippet only]. **Not sourced.** |
| X8 | Unreal Chaos destruction groups pieces into clusters by level, links neighbours in a connection graph with strain limits, and sets damage thresholds per level. Large clusters break before their children. | [source: Epic Games, "Destruction Overview", https://dev.epicgames.com/documentation/en-us/unreal-engine/destruction-overview, unread: snippet only (fetch refused)]; [source: Unreal forums, "Break Geometry Collection, smallest pieces first?", https://forums.unrealengine.com/t/break-geometry-collection-smallest-pieces-first/501898/3, unread: snippet only]. **Not sourced** (X3 is the read analogue). |
| X9 | Film capital-ship destruction used rigid-body breakup plus **many small explosions to convey scale**, in slow-motion shots. | [source: Computer Graphics World (The Last Jedi), https://digital.copcomm.com/i/977547/19, unread: snippet only]. **Not sourced.** |
| X10 | **Smoke and fire continuity:** emit trail particles in *world* space from anchor points on each falling chunk. Particles already emitted then stay where they were, and a moving chunk draws a continuous trail behind it. Local-space particles would instead be dragged along and read as a stuck sticker. | [source: Godot Engine, "GPUParticles2D" class reference, https://raw.githubusercontent.com/godotengine/godot/master/doc/classes/GPUParticles2D.xml, read 2026-11-16] — local_coords: "If [code]false[/code], particles use global coordinates; they will not move or rotate along the [GPUParticles2D] node". Also [source: Godot docs, "2D particle systems" (source rst), https://raw.githubusercontent.com/godotengine/godot-docs/master/tutorials/2d/particle_systems_2d.rst, read 2026-11-16] — "If enabled, particles will emit to local space, meaning that if the node is moved, already emitted particles are also affected." |
| X11 | **Off-screen parts:** keep every module attached to the hull's body frame and let the *whole* body tilt and sink out of frame. Never spawn a module as a separate sprite whose cut edge can enter view. Chunks may detach only along seams that are visible on-screen, and a chunk that reaches the frame edge carries its full art from the composite (D2). Because the composite always holds the whole hull, generating extra art is unnecessary. | Composite bounds: D2 (read). The policy itself: [UNSOURCED: plan/provenance-audit.md#CRE-4] |
| X12 | **Collapse choreography:** (a) the hull keeps its last velocity and gains a slow roll (ω of a few degrees per second) about a pivot near the damaged section; (b) primary breaks follow structural panel lines into 3–5 large chunks, each given v + ω×r (X1); (c) each large chunk sheds 2–4 smaller pieces later, as a second level; (d) small secondary explosions at the seams, with world-space smoke (X10). | Mechanics X1/X3/X10 (read). Tiering and numbers: [UNSOURCED: plan/provenance-audit.md#CRE-5] |

## 3. Shield wear readability (F)

| ID | Conclusion | Source |
| --- | --- | --- |
| F1 | **Flicker budget:** a flicker of the whole field must stay at or below 3 flashes per second, or stay below the flash thresholds, or cover only a small area. A field that spans much of the arena counts as a large area. | [source: W3C, "Understanding Success Criterion 2.3.1: Three Flashes or Below Threshold" (WCAG 2.2), https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html, read 2026-11-16] — "Web pages do not contain anything that flashes more than three times in any one second period"; a flash is "a pair of opposing changes in relative luminance of 10% or more"; area "no more than a total of .006 steradians" "(25% of any 10 degree visual field on the screen)". |
| F2 | Games apply the same limits. About 20% of the screen is the area that matters, saturated red has a lower threshold, and *prolonged* low-intensity flicker can also fail. So the "about to fail" flicker must be brief, low-contrast and not red-dominant. Prefer **dropout**, where sections go dark and stay dark, over strobing. | [source: Microsoft, "Xbox Accessibility Guideline 118" (photosensitivity), https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/118, read 2026-11-16] — "Flashes occur too frequently (approximately more than three per second)."; "Flashes take up a certain amount of the screen (approximately 20 percent or more)."; "Lower intensity flashing can also cause a failure if it's continued for an extended period of time." |
| F3 | **Never show shield health by colour alone.** Pair it with shape: thickness, gaps or dropout, and a pattern (hex cells disappearing). Add a sound cue as well (a hum whose pitch falls, and a "breach" sting). | [source: Microsoft, "Xbox Accessibility Guideline 103" (additional channels for visual and audio cues), https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/103, read 2026-11-16] — "Color alone should never be used to represent information."; critical content expressed through colour "also needs to be expressed by using at least one additional signifier such as shape, pattern, iconography, or text labels." |
| F4 | Precedent for state plus sound: a game pairs its visual depletion with a distinct audio pattern for "depleted". | [source: Microsoft, XAG 103, same URL, read 2026-11-16] — "visual cues such as the red attack indicators and health meter depletion are critical to gameplay. In addition to these two visual cues, audio cues such as the player grunting when hit and the beeping pattern for when the player's health has been completely depleted, are also present." |
| F5 | **Thin it out instead of shrinking it.** A shield effect built from layered parts (a fresnel rim, expanding hit rings, and a noise-mask dissolve) can map remaining strength onto the dissolve threshold and the rim strength. The field keeps its *footprint*, its coverage visibly erodes into holes, and each hit shows a ring at the impact. That reads as "wearing down", where narrowing reads as "retreating". | [source: cortiz2894, "flow-shield-effect" README, https://github.com/cortiz2894/flow-shield-effect, read 2026-11-16] — "Fresnel glow — edge highlight driven by view angle"; "Expanding ring — noisy geodesic wavefront that radiates from the impact point"; "Noise-based dissolve — shield materializes and dematerializes through a simplex noise mask". The mapping is ours: [UNSOURCED: plan/provenance-audit.md#CRE-6] |
| F6 | Fire a local impact effect at the hit point. Shield features can be switched off one by one to cut cost, which suits a low-end tier. | [source: Daniel Ilett, "shaders-stylised-shield" README, https://github.com/daniel-ilett/shaders-stylised-shield, read 2026-11-16] — "A VFX effect is also fired at the impact point."; "or turn some off if you want a less expensive shader!" |
| F7 | Halo layers several cues: flicker on damage, a warning on depletion, and colour shifts. | [source: Halopedia, "Sangheili personal energy shield", https://www.halopedia.org/Sangheili_personal_energy_shield, unread: snippet only (fetch refused)]. Fan wiki. **Not sourced.** |
| F8 | A commercial shield shader gives the low-energy state an "unstable and distorted" look as feedback that the shield is about to collapse. | [source: SF Studio, "Critical State", https://sf-studio.gitbook.io/unity-assets/interactive-scifi-energy-shields/shader-sf-energy-shield/critical-state, unread: snippet only]. **Not sourced.** |
| F9 | **Implementation path:** a fragment shader on `Paint.shader` (rim, noise dissolve, hex cells), with HP as a float uniform. Reuse one `FragmentShader` across frames. Pre-load the program before the fight, because on Skia, which is what web uses, it compiles at load time. | [source: Flutter, "Writing and using fragment shaders", https://docs.flutter.dev/ui/design/graphics/fragment-shaders, read 2026-11-16] — "You can reuse a `FragmentShader` object across frames; this is more efficient than creating a new `FragmentShader` for each frame."; "When targeting the Skia backend, loading the shader might be expensive since it must be compiled to the appropriate platform-specific shader at runtime." |
| F10 | Fade the field's opacity through the paint's own colour alpha or shader alpha, not through an `Opacity` widget or `saveLayer`. | [source: Flutter, "Performance best practices", https://docs.flutter.dev/perf/best-practices, read 2026-11-16] — "Avoid using the `Opacity` widget, and particularly avoid it in an animation."; "it's usually faster to just draw them with a semitransparent color." |
| F11 | Under reduced motion, replace the shimmer and flicker with a static thickness and gap pattern. | [source: MDN, "prefers-reduced-motion", https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion, read 2026-11-16] — "used to detect if a user has enabled a setting on their device to minimize the amount of non-essential motion." |

## 4. Performance on mobile web (P)

| ID | Conclusion | Source |
| --- | --- | --- |
| P1 | **Texture size:** 4096 is the safe WebGL maximum. Some low-end devices offer no more than that, even where desktops offer 16k. Keep the composite at or below 2048 on its long edge, for margin. | [source: MDN, "WebGL best practices", https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices, read 2026-11-16] — "In practice, effectively all systems support at least the following: … MAX_TEXTURE_SIZE: 4096"; "Your desktop may support 16k textures but lower-end systems may not". |
| P2 | Mipmaps (used by `FilterQuality.medium`) add about 33% memory. | [source: MDN, same page, read 2026-11-16] — "Mipmaps are cheap on memory (about 33% overhead for square textures)". |
| P3 | **Memory arithmetic:** RGBA8 uses 4 bytes per pixel. 2048² × 4 = 16,777,216 B = **16 MiB**, or ≈21.3 MiB with mips. A 1600×1400 composite (the 800×700 hull at 2×) takes 8.96 MB, or 8.5 MiB. At 3× (2400×2100) it would exceed 2048 and take 20.2 MB. **Recommendation:** compose at 2× and cap the scale so neither edge exceeds 2048. | Arithmetic: [UNSOURCED: plan/provenance-audit.md#CRE-7] |
| P4 | **Real device ceiling:** on one Adreno 610 phone, a 4096×4096 `toImageSync` target hung the GPU, while 2900×4096 drew. 2048-class targets are well inside the safe range. | [source: flutter/flutter#195750, "[Impeller] Android OpenGL ES: toImageSync into a 4096x4096 target hangs the GPU on Adreno 610 (Galaxy A23)", https://api.github.com/repos/flutter/flutter/issues/195750, read 2026-11-16] — "// The offscreen target. 4096 x 4096 hangs; 2900 x 4096 draws." | P5 | **Do not re-compose every frame.** Each `toImageSync` call allocates a fresh GPU texture, at least on Impeller. Do it at most a few times per fight, and dispose the old image. | [source: flutter/flutter#193941, "[Impeller] Picture.toImageSync allocates a new GPU texture on every call", https://api.github.com/repos/flutter/flutter/issues/193941, read 2026-11-16] — "Every `toImageSync` call allocates a fresh texture:" (open, filed 2026-10-07) |
| P6 | Dispose superseded composites. | P7 | Avoid `saveLayer`: an offscreen buffer with a render-target switch per frame. That is exactly what a per-frame "compose the layers, then warp" via `saveLayer` would do. ## Unsourced engineering choices (to add to `plan/provenance-audit.md`)

- **CRE-1:** Separate per-layer warps drift because each layer has its own copy of shared edges. One indexed mesh
  over one composite cannot open a seam, because adjacent triangles share vertices (D4).
- **CRE-2:** Hull grid density of about 12×10 cells (≈130 vertices) for an 800×700 hull. Refine it by profiling (D14).
- **CRE-3:** Bend amplitude of ≤1.5° equivalent shear or turn, cycle ≥3 s, eased (sine), with the stern lagging the
  bow by about 0.2–0.4 s for follow-through, and no oscillating wobble (D18, D20).
- **CRE-4:** Off-screen policy. Every module stays bound to the hull frame, and only on-screen seams detach. The
  composite always holds the full hull, so no partial asset can be revealed (X11).
- **CRE-5:** Collapse tiers and numbers: a roll of a few °/s, 3–5 primary chunks along panel lines, then 2–4
  secondary pieces per chunk, small explosions at seams, and world-space smoke (X12).
- **CRE-6:** Shield HP mapping. Keep the footprint and radius constant. Rim thickness and alpha are proportional to
  HP. The noise-dissolve threshold is set to (1 − HP), so holes grow. Hex-cell dropout starts below 50% HP. Any
  whole-field flicker stays ≤3 Hz, low-contrast and not red-dominant. Crackle stays local (small area). A
  falling-pitch hum and a breach sting carry the same information as sound (F2, F3, F5).
- **CRE-7:** Texture memory arithmetic and the 2× / ≤2048 cap (P3).
