# Bonus levels: blocker log (agent A)

Written while building the `bonus-levels` framework and bonus level #1 (Supply Run) from the project's own
documentation, without asking anyone. Each entry says what was missing, wrong or ambiguous, what I did instead, and
what would remove the blocker. "Significant change" marks the ones that need a structural decision, not a patch.

Not verified by me: the game in a browser or on a phone, any audio by ear, `npm run build`, `npm run test:worker`.
Verified: `flutter analyze`, the full `flutter test`, `openspec validate bonus-levels --strict`, the review strips by
eye.

## A. Model structure

1. **A level is not data. Significant change.** A sector's content is formulas in `DifficultyPolicy` plus code spread
   through the 4 241-line `lib/game/model.dart`. The waves-per-sector formula alone exists three times (the
   `wavesPerLevel` getter, `wavesFor`, and inline in `restoreCheckpoint`). To let a bonus level change waves, rosters,
   reinforcements, sentinels, elites, species, drops, score and fire rate I had to put one-line hooks in about 20 places.
   They are identity without a plan, and tested, but every new kind of rule a level wants is another hook in that
   file, which other agents (the boss work) edit at the same time.
   *Would remove it:* a `LevelDef` that regular sectors also go through, so a bonus level is one more definition.
2. **`enum Power` is closed. Significant change.** The kill-drop cycle indexes `Power.values`, and the pickup badge,
   the ship's module rows, the HUD glyphs, the hint art and the comms variants all switch on it. A sixth value would
   change every run's drops and need art in three atlases. Bonus-only powerups therefore live beside the enum
   (`BonusPowerDef`, `Pickup.bonus`, their own timers), and the cabinet's power-status row cannot show them; they show
   as a badge and ring beside the ship.
   *Would remove it:* a power registry (id, badge, colour, exclusions, effect primitives) that the five regular powers
   are entries of.
3. **A run had no seed.** The request says "seeded, deterministic", but `ArcadeModel` is built once with the fixed
   seed 1982 and `start()` does not reseed, so "the run's seed" did not exist. I added `start(runSeed:)`, a clock
   source in `main.dart` (`arcadeRunSeed`) and `test/flutter_test_config.dart`, which makes every page-level test
   start unseeded runs. Without that file, 17 test files that pump the app would have met bonus levels and run
   modifiers at random.
   *Open:* the interlude planner has its own separate per-run clock seed; the two are not unified.
4. **The homing-missile pickup is outside the power system.** It is a `HomingPickup` in the ground war, not a
   `Power`, so run modifiers cannot ban it or make it the only drop. Left as it is.
5. **Nothing documents how powers drop.** The rule (every eighth kill, cycling the enum; a sentinel shot down in a
   dive; the carrier's crate roll 70/10/10/10) is only in code. The README still describes three powers; there are
   five.

## B. Specs and documentation

6. **No `CLAUDE.md` or `AGENTS.md`.** The README's "Project layout" lists ten paths; `lib/comms`, the flow director,
   the `part of 'model.dart'` convention and the `// --- <change>` section markers are not mentioned. I learned the
   conventions by reading code.
7. **The main specs are far behind.** `openspec/specs/` has seven capabilities; about 38 changes are unarchived, and
   `squad-comms` exists only as deltas inside changes. What a transition is *today* has to be reconstructed from
   `cinematic-flow`, a "superseded in part" note pointing at `playtest-fixes` §10.3 (archived) and
   `transition-ascent`. The rule this task depends on most ("transitions speak only by radio, no floating text") is
   in a MODIFIED delta of an unarchived change.
   *Would remove it:* archive what has shipped, so `openspec/specs/` is the truth.
8. **`openspec/config.yaml`'s context is the 2025 game** ("four demon-swarm levels … three lives"). Every OpenSpec
   skill injects it.
9. **The `openspec-propose` skill forbids what the task asks.** It says planning only: "Do not edit project code …
   stop." The assignment was to design and implement in one pass, so I wrote the artifacts by hand in the skill's
   format instead of invoking it. The six skill files are also modified and uncommitted in the main checkout
   (generated by OpenSpec 2.0.0 over 1.14.3 files), so which version is authoritative is unclear.
10. **`--strict` rejects the project's own spec style.** Requirement paragraphs over 500 characters are warnings
    that fail strict validation; existing deltas are written as long paragraphs. Six of my requirements had to be
    split or shortened after the fact.
11. **"No floating text" leaves a bonus level almost unannounced.** With placeholder voices the entry call says
    "Salvage on the field. Quick pass, then regroup." The player learns it is a bonus level from that line, the dawn
    grade and the parachutes. The spec's wording ("no text … without a window or toast") suggests a toast would be
    allowed. I did not add one. *Operator decision.*
12. **Score-board fairness is undefined.** Nothing says whether runs that differ by chance may share a board. I
    capped what a bonus level adds and kept modifiers rare (12 % of runs), and did not touch the score API. A board
    row does not record the run's modifier or seed.

12a. **`openspec validate --all --strict` already fails on `game`.** The README lists it as a validation step, but 7
    of 46 items fail before this change (main specs `arcade-combat`, `arcade-presentation` and
    `third-party-licence-demucs-weights-unstated`; changes `comms-middle-ground`, `fog-restoration`,
    `gameplay-round-3`, `ground-blocks-runtime`). `bonus-levels` itself validates; I left the others alone.

## C. Radio pipeline

13. **Special lines cannot be heard yet (tillandsias#1103).** The placeholder mechanism plays the borrowed clip
    *with the borrowed clip's own words*. So the 23 "special radio lines" exist as text in
    `plan/audio-studio/voice-batch-pending.md`, and in the game they are 23 well-chosen existing lines. The choice
    is limited to the 574 recorded clips: there is nothing recorded about convoys, crates or bonus rules, so the
    Supply Run borrows the four `salvage` lines heavily.
14. **The line bank's schema is documented only inside the data.** The field list is one long `comment`
    string in `art/comms/lines.json` plus the pipeline's docstring. I copied `frontCall`'s spec without knowing what
    `transmission`, `overlap` or `chain` would do to a bonus line.
15. **A trigger name is never checked against an emitted event.** A typo in `lines.json` or in a level id produces
    a line that never plays, silently. My test checks that each catalogue level and modifier has its trigger; nothing
    checks the general case.
16. **A hard-coded count breaks on every new borrowed line.** `test/comms_director_test.dart` expects exactly 29
    borrowed lines (now 52). Two agents adding lines in parallel will both edit that number, and both regenerate
    `lib/comms/comms_bank.dart` (1 700 lines, one per line) and the pending list: three guaranteed merge conflicts.
    *Would remove it:* derive the count from `lines.json`; keep generated files out of parallel branches or
    regenerate them at integration.
17. **Borrowed clips can repeat back to back.** `bonusCleared.supplyRun` borrows `levelClear` clips, and the regular
    `levelClear` trigger fires a few seconds later with its own pick of the same clips. The director's recency rules
    are per line id, not per clip. Not fixed.
18. **The run-modifier announcement is untested against the opening tip.** It is sent on the first combat frame; the
    opening tip hushes the channel. I verified the event, not what is heard. It also repeats when a run is resumed.

## D. Art and music pipelines

19. **No art route for a small new icon.** A bonus powerup needs a pickup badge. The atlas generators are Python
    scripts with their own palettes and the task rules out generation, so the two badges are existing cells of
    `combat.png`'s pickup row, recoloured (the shield's U as a coral magnet, the large orb doubled as gold coins). The
    atlas layout is documented only in comments in `sprite_atlas.dart`.
    *Would remove it:* a documented "add one 64 px cell" recipe, runnable without the GPU.
20. **A bonus level cannot have its own backdrop or music yet.** Backdrops come from `tools/flyover_assets.py` (GPU
    jobs) and are keyed by sector index throughout `sector_background.dart`; music cues are requested in `main.dart`
    as `audioCue('level', sector, 1, route)`. I gave `BonusLook` a colour grade and an unused `cue` field. Wiring
    either needs the sector index to stop being the key. **Significant change.**
21. **The grade is a guess at "special".** A soft-light wash and a horizon light over the same sector reads as
    another time of day, which is what I wanted, but it is one grade for all three sectors and it was tuned on three
    still frames.

## E. Calibration

22. **Flat score numbers were wrong, and no document would have told me.** The first Supply Run paid 6-7 k where the
    sector it replaced pays 10-40 k: the "bonus" level was a score penalty. I found it only by measuring, then
    introduced `sectorPar` and awards as shares of it (design §6.1).
    `plan/difficulty-calibration.md` records clear times and lives, not what each sector pays.
23. **The bonus level is not calibrated.** `tools/analyze_difficulty.dart` and `tools/profile_difficulty.dart` do
    not know bonus levels. My numbers come from a weaving, invulnerable auto-fire pilot, not the protected pilot the
    project calibrates with. The Supply Run lasts only 18-28 s for that pilot (four to six of eight crates), which is
    probably too short.
24. **`sectorPar` underestimates.** It counts opening rosters; a real clear pays 1.7-2.6 × par because of
    reinforcements, sentinels and dive bonuses. The Supply Run's shares (1.0 + 0.3, cap 1.5) compensate by hand. On
    the second tour a flawless Supply Run still pays only about two thirds of its sector.

## F. Tooling (Tillandsias forge)

25. **`flutter` failed once with `runtime_unavailable: podman failed at step list (timeout)`** while a full
    `flutter test` ran in the background and I started a second one. A retry worked. The message does not say that
    concurrency was the cause.
26. **The bash policy hook drops the whole command.** `rm $W/test/x.dart` was refused ("unresolvable rm target"),
    which is fair, but the same command also wrote a file with a heredoc and ran the tests; all of it was dropped,
    and the next command failed on the missing file.
27. **The repository is not `dart format`-clean.** `dart format lib` rewrites 28 files I never touched. There is no
    stated formatting rule, so an agent that formats before committing produces conflicts in other agents' files. I
    reverted them and formatted only my own files.
28. **Tool language.** The global rule is Lua > Rust > Go, but the pipeline I had to run
    (`tools/comms_pipeline.py dart`) is Python. I ran it as the project does and wrote my own edit helpers in Lua.
29. **The full test run takes 3 min 20 s** and prints about 1 000 lines; the only reliable verdict is grepping for
    "Some tests failed".
30. **Review strips are per-test boilerplate.** Each `*_review_test.dart` copies 100 lines of atlas loading
    (`_decode`, `_scene`, `_frame`, `_png`). I copied them again. A shared `test/support/review_scene.dart` would make
    a strip a 30-line test, which matters when every bonus level needs one.

31. **"Rebase before finishing" and "push the interface note first" cannot both be done.** The git mirror rejects
    non-fast-forward updates of a work branch, so a branch that was pushed early (as the parallel agent needed) cannot
    be rebased and pushed again. I merged `origin/game` into the branch instead; the tree is identical to the
    rebased one I tested.

## What I would change first

1. Archive shipped changes and refresh `openspec/config.yaml`, so the specs describe the game (7, 8).
2. Decide the announcement question (11) and the score-board question (12).
3. Make the borrowed-line count derived and regenerate generated files at integration (16).
4. Plan the `LevelDef` and power-registry refactors before a third bonus level (1, 2, 20).
