# Asset pipelines

How the shipping art is produced and how to regenerate it. Each section owns its own family of assets; research notes on models, licences and consistency techniques live in [asset-pipeline/](asset-pipeline/README.md).

## Backgrounds (flyover with a horizon)

The oblique 3/4 flyover backgrounds (see "Backgrounds: oblique flyover with a
horizon" in [style-guide.md](style-guide.md)) are generated by a reproducible
local ComfyUI pipeline. Every input is committed; the GPU stage is deterministic
for a fixed ComfyUI build, model set and seed (rerunning the mid-ridge strips in
this pass reproduced the shipped atlas byte for byte), and every later stage is
deterministic integer/NumPy work.

### Layout

| Path | Role |
| --- | --- |
| `art/families/flyover-backgrounds.json` | The family spec: per sector the mid-ridge and wall strip prompts, the ground-plane prompt, props, five routes × two landmarks and two creature species; seeds; sizes; luminance and chroma caps; wall width; ground macro modulation. |
| `art/workflows/backgrounds/strip-sheet.json` | Strips (ridges, walls): SDXL base + pixel-art-xl LoRA img2img from a layout sheet (`$init_image`, KSampler `$strength`), an in-graph **roll by half height** (two `ImageCrop` + two `ImageCompositeMasked`) and a masked repaint of the middle band (`$mask`, `SetLatentNoiseMask`), so the result tiles vertically. |
| `art/workflows/backgrounds/ground-tile.json` | Ground plane: the same, then a **second roll by half width** and a repaint of the vertical band (`$mask_v`), so the tile is seamless in x and y. |
| `art/workflows/backgrounds/sprite-transparent.json` | Transparent sprites (landmarks, props, creature poses): SDXL base + pixel-art-xl + LayerDiffuse conv injection; saves RGB (`10_…`) and decoded alpha (`12_…`). |
| `art/workflows/backgrounds/txt2img-pixel.json` | Plain txt2img probe used to tune prompts. |
| `art/palettes/flyover-<sector>.json` | Bounded palettes (43 colours) median-cut from each sector painting. |
| `art/families/flyover-runs.json` | Provenance of every ingested run: workflow, prompt, negative prompt, seeds, strength, models and SHA-256 of each raw output. |
| `tools/flyover_assets.py` | The driver (below). |
| `assets/images/flyover-<sector>.png` | Strip atlas, 384×384: rows mid (ridges) and wall; columns three left variants then their mirrors for the right side. |
| `assets/images/flyover-<sector>-ground.png` | Ground macro tile, 768×768 palette PNG (a 4×4 repeat of the 192-texel seamless tile under smooth periodic light modulation). |
| `assets/images/flyover-props.png` | Shelf-packed props and route landmarks for all sectors. |
| `assets/images/flyover-creatures.png` | One row per species: 8 frames (walk/crawl 0–3, duck 4–5, burrow 6–7) and the same 8 mirrored. |
| `lib/game/flyover_atlas.dart` | Generated metadata: sprite rects, creature rows, layer widths and the per-row edge of every strip. Never edit by hand. |
| `art/contact/flyover-contact.png`, `flyover-landmarks.png` | Contact sheets: every strip (tiled to show the seam), ground crops, sprites and creature frames; and a routes × landmarks grid. |

### Rerunning

```bash
# Keep the venv and raw generations OFF the checkout (the forge's /home/forge/src is a small tmpfs).
python3 -m venv $SCRATCH/asset-venv && $SCRATCH/asset-venv/bin/pip install pillow numpy
PY=$SCRATCH/asset-venv/bin/python
export FLYOVER_RAW=$SCRATCH/flyover-raw   # ingest copies raws here (default .cache/flyover-raw)
$PY tools/flyover_assets.py palettes   # sector palettes from the paintings
$PY tools/flyover_assets.py layouts    # layout sheets + seam masks -> /work/tmp/imagegen/flyover/inputs
$PY tools/flyover_assets.py jobs       # 90 jobs -> /work/tmp/imagegen/flyover/jobs.json
# GPU stage, either:
$PY tools/flyover_assets.py run        # direct ComfyUI HTTP backend (COMFY_URL, default http://studio:8188)
#   (--only strip/,plane/,landmark/krybor limits the jobs; outputs land in /work/tmp/imagegen/flyover/http)
# or run each job through studio.run_workflow with the same workflow, inputs,
# strength and overrides, and save {job id: [output paths]} as results.json.
$PY tools/flyover_assets.py ingest [--results results.json]   # copy raws to $FLYOVER_RAW, record provenance
$PY tools/flyover_assets.py pack       # process + atlases + Dart metadata + contact sheets
flutter test test/flyover_background_test.dart test/sector_background_test.dart test/flyover_perf_test.dart
```

`studio.run_workflow` resolves workflow paths against the project checkout, so
from a worktree pass the worktree-relative path. The HTTP backend binds the same
placeholders (`$prompt`, `$negative_prompt`, `$seed`, `$strength`, `$init_image`,
`$mask`, `$mask_v`, and `$node:<id>.<input>` overrides) the studio tool does.

### Processing stages (`pack`)

1. **Layouts.** Strip sheets hold three 64×192-logical left banks (8 px per
   logical pixel) with a seeded, vertically periodic contour; their interiors
   are textured from the sector painting. Wall layouts are slim (base 15
   texels) and *broken*: seeded bites out of the inner edge and detached
   boulders beyond it. Ground layouts mirror the painting's foreground band;
   the ground job runs at strength 0.95, so the prompt dominates.
2. **Strips.** Box-downscale, un-roll, normalise under the luminance cap and
   snap to the sector palette under the luminance/chroma caps. Ridge alpha keeps
   pixels connected to the outer edge; wall alpha keeps detached boulders and
   drops specks under 6 px. The per-row edge is exported for placement.
3. **Ground.** Box-downscale to 192 texels, un-roll in x and y, tile 4×4,
   multiply by smooth periodic low-frequency light (±40%) so the far plane
   never shows a regular grid, quantise (cap 0.13, chroma 0.22), save as a
   palette PNG.
4. **Sprites.** LayerDiffuse alpha → crop → box downscale to the spec height →
   palette quantise under caps (landmarks 0.40, props 0.34, creatures 0.42 /
   chroma 0.34; saturated warm colours are reserved for hostile fire) →
   binary alpha → despeckle. Creatures get a dark outline whose upper-left
   pixels take a muted light colour (rim light).
5. **Creatures.** One generated pose per species (14–15 texels tall) becomes
   eight discrete frames: four-frame walk/crawl/burrow gait, two duck frames,
   two burrow frames.
6. **Pack.** Strip atlases with mirrored right sides, ground tiles, a sprite
   atlas, a creature atlas with mirrored frames, the Dart metadata and the
   contact sheets. New asset weight is about 1.2 MB (ground tiles ~0.75 MB).

### Runtime contract

`lib/game/flyover_background.dart` uses one camera for everything below the
horizon (y = 172 + 348·z0/z, scale z0/z). Per sector per frame: one baked sky
image, one ground rect with a perspective `ImageShader`, one 110 px fog
gradient, one ridge `drawAtlas` (rotated mid strips), one wall `drawVertices`
mesh, one landmark/prop `drawAtlas` and one creature `drawAtlas`. Strip variants
come from a no-repeat seeded sequence; landmarks, props and creatures are placed
per world segment from stateless seeded hashes, so any flight distance draws
the same picture on every device. Adding a sector or route means adding spec
entries and rerunning the pipeline.

## Sprites

Combat creatures, sentinels, the carrier, the player ship, its cannons, muzzle flashes and every projectile. The contract (layouts, palette, timings, frame selection) is [sprite-atlas.md](sprite-atlas.md); the visual rules are in [style-guide.md](style-guide.md#creature-direction-gargoyles-not-birds).

### Principle

Silhouettes, poses, armour, insignia, weapon mounts and effects are **authored deterministically** in Python on the logical grid, because thirty directional flight frames per damage state, molts, flashes, death sequences and recoil frames must stay aligned pixel for pixel across hundreds of cells. Since the gargoyle round the creatures and sentinels come from `tools/gargoyle_rig.py`, a tiny 3-D rig (volumes, bat-wing membranes, decals) rasterised with a z-buffer and a quantised key light onto the bounded palette: left and right banking frames are real renders of the same anatomy, so asymmetric details stay on their side without mirroring tricks, and wing in-betweens come from joint-angle tables (`FLAP`, `GLIDE`, `COCKED`, `DIVE` in `generate_sprites.py`; `STROKE`, `WARNING`, `CHARGE`, `DIVE`, `RUSH` in `generate_sentinel_sprites.py`). ComfyUI contributes **concept and shading detail only**: gargoyle keyframes are finished onto the grid as a four-level luminance map that nudges the key-light value of hide pixels (stony, leathery texture) before quantisation. AI output never replaces an authored outline, face, insignia or palette, so every frame stays readable at phone size.

### Rerun

A Python venv with Pillow, NumPy and SciPy (`python3 -m venv <dir> && <dir>/bin/pip install pillow numpy scipy`; keep it outside `/home/forge/src`, which is a small shared tmpfs), then:

```bash
python tools/sprite_pipeline.py offline     # finish -> atlases -> sheets; no GPU, byte-identical output (~45 s)
python tools/sprite_pipeline.py all         # keyframes -> edits -> finish -> atlases -> sheets
python tools/sprite_pipeline.py keyframes   # or any single stage: edits, finish, atlases, sheets
flutter test test/gargoyle_review_test.dart test/carrier_review_test.dart && python tools/sprite_pipeline.py screens   # in-engine review sheets
```

GPU stages post the committed workflows to the project's ComfyUI studio over its HTTP API (`$COMFYUI_URL`, default `http://studio:8188`, the same server `studio.run_workflow` drives) with the seeds and prompts above, so the same models and seeds reproduce the candidates; raw outputs go to `$SPRITE_PIPELINE_CACHE` (default `~/.cache/demon-attack/sprite-pipeline`, never the repo). Agents can run the same workflows through `studio.run_workflow` / `studio.queue_workflow` (`$prompt`/`$seed` overrides, `inputs: {input: <keyframe>}` for edits) and drop the outputs into the cache as `<species>-<seed>.png`. `edits` skips molts that already exist under `art/sprites/sources/molts/`; delete them to regenerate. Finishing is CPU-only and deterministic: colour-key matte from the border, largest component, head/torso window (central 34 % of the width, top 80 % of the height), box-sampled onto the hide box `(20, 14)–(44, 52)` of the 64-grid and quantised to four levels at the 20/55/85 % luminance quantiles.

Stages in detail:

1. **keyframes**: four candidates per species at seed, seed+1, … (prompts.json); pick in `selections.json`.
2. **edits**: three molt variants of the selected keyframe (glowing cracks; badly cracked with a chipped horn and torn wings; shattered with a broken horn and shredded wings); used as molt detail maps.
3. **finish**: → `detail/<species>.png` and `detail/<species>-m<k>.png`.
4. **atlases**: `palette.json`, then the four generators. The rig is deterministic (no randomness, fixed tables); Wan2.2 VACE in-betweening and ControlNet pose guidance were considered and not used, because the rig already produces exactly aligned in-betweens and turnarounds for every direction and damage state, and that spares the shared GPU.
5. **sheets**: contact sheets for review.
6. **screens**: composes the in-engine review frames (not part of `offline`; it depends on a Flutter test run).

### Verification

`flutter test` covers atlas sizes, binary alpha, the bounded palette, the gargoyle atlas contract (30 distinct flight frames per damage variant, right banks are not mirrors of left banks, folded upstroke narrower than the level downstroke, every flash, action and elite cell present), the motion state machine (hysteresis without flicker, glide when sinking, longer downstroke when climbing, priority of actions), sentinel pose rules (distinct frames, folding recovery and rush, warnings confined to the creature) and wing-cannon alternation. Visual review uses `test/gargoyle_review_test.dart`'s phone-size renders (every species left / neutral / right in downstroke and upstroke, glides, damage states, elites, combat over each sector background) and the contact sheets above.

## Ground forces

The demon ground army, the allied human ground units that skirmish with it,
their ground effects and the demon ground-to-air missile share one atlas,
`assets/images/ground-forces.png`. They drive along the oblique ground plane
of the flyover (see "Backgrounds" above) and use its camera: drawn with
`drawAtlas` at `2·z0/z` arena units per texel and modulated by the distance
fog. Like the combat sprites, **silhouettes, launchers and every frame are
authored on the texel grid** (`build_*` functions in the driver). That keeps
the move cycles, telegraph, fire and wreck/limp frames aligned pixel for
pixel. The SDXL + pixel-art-xl + LayerDiffuse keyframe of each unit
contributes only a −1/0/+1 shading texture on the hull ramp (high-pass
luminance, thresholded at ±1.4 σ). The keyframes came out top-down, or facing
the wrong way, or as people instead of vehicles. None gave a 3/4 vehicle
facing screen right with a launcher that can be lifted, at 20 texels, so AI
silhouettes are not used.

### Processing stages

1. **Keyframes.** One LayerDiffuse transparent keyframe per unit, missile
   and explosion, at seed, seed+1 and seed+2. The pick is recorded as
   `selected` in the spec.
2. **Sources.** The pick is cropped to its alpha (≥140), box-downscaled to
   ≤64 px and stored as RGBA.
3. **Texture.** The source is box-sampled to 32×24 and high-passed. It
   shifts hull texels h1–h3 by one ramp step in body space, so the texture
   rides the gait bob.
4. **Authoring.** The integer code grid is built from primitives: lit 3/4
   boxes (top face h3 with an h4 front edge, side h2, underside and right end
   h1), wheels with six notches turning 15° a frame, and treads with crawling
   links. Two-group leg gaits lift one leg group and swing the other. Tubes
   are rasterised at the launcher angle (idle / raised / recoil / post-fire
   per unit), with seams and warhead noses. Accents come from reserved codes.
5. **Frames.** Exhaust puffs drift and thin one step per move frame, so the
   cycle loops. Telegraph frames re-run the builder with the launcher raised
   and paint the warhead glow. The fire frame adds a warm cross flash and
   smoke; post-fire adds a smoking muzzle. Wrecks drop the launcher and darken
   the hull, quench the accents, tear the top along a seeded profile and
   punch holes. A scorch ellipse goes underneath, and there are two frames of
   flame tongues (one wide, heights flicker), embers and dark smoke. Allies
   are never wrecked: the hit frame lifts the hull one step and adds cyan
   sparks. Limp frames dent the hull, kill half the cyan lights, switch the
   builder to its damaged variant and add sparks and grey smoke. Allied fire
   is cyan only.
6. **Finish.** A one-texel dark outline goes on, with a rim light over lit
   top edges, so silhouettes separate from the very dark ground tiles. The
   unit is bottom-centred, and codes map to colours. Demon hulls use a
   five-step **mid-value** ramp (luma 0.06–0.40, rim 0.56, chroma ≤ 0.36).
   It is picked from `art/palettes/flyover-<sector>.json` plus the reserved
   demon-steel greys, which fill in where a sector palette has no mid values
   (Ember). Bright warm accents (eyes, vents, cracks, runes, warheads) come
   from the reserved warm set. Allies use the reserved grey-blue hull (a
   lighter ramp than the demons') and the cyan `#70F5D5` family. Effects, the
   missile and the pod use the smoke ramp as iron plus the warm or cyan set.
7. **Effects.** The explosion and small blast are seeded value-noise heat
   fields with smoke shaded from the upper left and flung debris. The scorch,
   launch flash, tracer spark, puffs, pod and missile are procedural.

### Runtime contract

`GroundAtlas` (generated; same API every run) gives the file, the grid, the
row helpers and every column constant. A ground unit is one `drawAtlas` rect
`(col·32, row·24, 32, 24)`, anchored at its bottom centre on the ground
point. It uses the landmark camera (`y = 172 + 348·z0/z`, scale `2·z0/z`) and
colour `fog(z)` with `BlendMode.modulate`, mirrored for the right band. Move
frames loop 0→3. The missile cell is meant to be drawn centred and scaled up
with nearest-neighbour as it closes on the camera, trailed by puffs 2→4. The
escape pod and smoke puffs (row 8, cols 10–11) are free sprites.

## Squad comms portraits

The video-call portraits of the squad comms cast (19 rows: 14 fleet and ground humans, 5 gargoyle demon officers, in `art/comms/cast.json` order) live in two atlases. `assets/images/comms-portraits.png` holds **128 × 128 logical px** cells, drawn at an integer scale (2× on desktop side panels). `assets/images/comms-portraits-small.png` holds 48 px cells for the phone overlay at 1×. Each row has twelve frames in `CommsFrame` order (`lib/comms/comms_types.dart`): 0 idle, 1 blink, 2–4 talk A/B/C (mouth opening), 5 talk D ('oo'), 6 shout, 7 grunt (the demon roar, or human alarm), 8 happy (demon smug gloat), 9 worried (demon alarmed snarl), 10 tilt left and 11 tilt right. `lib/comms/comms_portraits.dart` is generated, with the image paths, cell sizes and the row of each character id.

### Principle

ComfyUI makes one keyframe per character and five expression edits of it. Everything after that is deterministic CPU work on the logical grid, so lip sync and blinks never jitter. Each edit is registered to the idle frame by the integer shift that minimises the difference. It is then composited **only inside the face box** (only the eye box for the blink), so hair, helmet, uniform and wings stay identical across all twelve frames. Talk frames squash the shout mouth (its tight box around the dark opening, lips and teeth) to 35, 65 and 100 % of its height with nearest-neighbour row picks, centred on the closed mouth; the 'oo' frame is 80 % high and 60 % wide. Only pixels that differ from idle are painted. Tilts shear the rows above the chin pivot by ±5°: each row shifts horizontally, so its pixel clusters stay intact and nothing is resampled by rotation. The eye box comes from the blink edit's difference and the mouth box from the connected dark opening of the shout edit below the eyes, both searched near the centre column; `picks.<id>.eyes` / `.mouth` override either. The boxes used are written to `art/comms/portrait-faces.json`. Every frame then gets the combat sprites' top-left rim light (silhouette pixels facing up or left step 40 % toward ivory) and a 1 px midnight-ink outline, and snaps to a bounded palette. That palette is the combat palette of `tools/sprite_kit.py` plus 36 portrait colours (seven-step and five-step skin ramps and hair, olive, navy, green, crimson and bone ramps). The small atlas is a premultiplied area downsample of each finished frame, snapped to the same palette.

| `art/comms/sources/<id>-{key,blink,shout,grunt,happy,worried}.png` | Inputs of record: each picked image with its BiRefNet alpha, cropped to the keyframe's head-and-shoulders square and stored at 2× the logical grid (256 px, adaptive 160-colour PNG) |
| `art/comms/portrait-faces.json` | Generated: mouth and eye boxes per character |

### Rerun

```bash
PY=$SCRATCH/venv/bin/python        # pillow + numpy + scipy, outside /home/forge/src
$PY tools/comms_portraits.py offline   # pack + sheet from art/comms/sources: no GPU, byte-identical
$PY tools/comms_portraits.py all       # keyframes -> edits -> matte -> ingest -> pack -> sheet
$PY tools/comms_portraits.py keyframes [id,id]   # single stages also: edits, matte, ingest, candidates
```

GPU stages post the committed workflows to the studio over HTTP (`$COMFYUI_URL`, default `http://studio:8188`) and write raw outputs, each with a provenance sidecar (workflow, seed, prompt, models, SHA-256), to `$COMMS_PORTRAIT_CACHE` (default `~/.cache/demon-attack/comms-portraits`, never the repo). `candidates` writes a review sheet of every keyframe candidate there. Stages:

1. **keyframes**: three candidates per character at seed, seed+1, seed+2 (`count`/`seed_base` per pick for rerolls). The prompt is the style + the human or demon fragment + the cast `look` + an optional per-pick `extra`.
2. **edits**: an optional `base_edit` first (Qwen edit that corrects age or colour but keeps the design: admiral and march aged, skarn recoloured coral, morth gold and bone with a third eye, ulgra crimson), then blink, shout, grunt/alarm, happy and worried. Each prompt is the shared "keep everything, change only the expression" preamble plus the expression.
3. **matte**: BiRefNet alpha for the base and every edit.
4. **ingest**: crop + alpha → `art/comms/sources/` (the head crop is computed once from the keyframe matte and shared by all frames).
5. **pack** / **sheet**: the CPU stages above.

Wan2.2 VACE in-betweens were not used. The talk cycle is a mouth-only repaint and the tilts a shear, both exactly aligned on the grid, which a video model cannot guarantee. Skipping it also spares the shared GPU.

### Verification

Judge the sheet at native size: 128 px at 2× for desktop panels and the 48 px atlas at 1× for phones. Check that eyes and mouth read at 48 px, that the face does not move outside the face box between frames, and that the shout, roar, happy and worried faces differ clearly.

## Wide-screen backdrops

The scenery beside the centred column on desktop (`lib/widgets/widescreen_backdrop.dart`, design in [style-guide.md](style-guide.md#wide-screen-backdrops)). Nine 2.4:1 panoramas (four menu scenes, five sectors) and one tileable command-wall texture, all original, from the project's ComfyUI studio and finished onto a small pixel grid.

### Principle

Composition is authored, texture is generated. Each menu scene starts from a seeded layout drawn with flat primitives (sky gradient, planet, ridges, capital-ship wedges, bat-winged gargoyle silhouettes, medal alcoves, fireworks). Each sector scene starts from its own sector painting: the rows below `crop_top`, mirrored out to 2.4:1, so the side scenery has the sector's palette, horizon and materials. SDXL + pixel-art-xl repaints the layout img2img at a fixed seed and denoise (0.38–0.45 for menus, which keeps the silhouettes; 0.35 for sectors, which keeps the painting's fine pixel detail while repainting the mirrored halves; 0.5 for the wall). The finish is CPU-only and deterministic: box sampling onto 768 × 320 logical pixels (96 × 96 for the wall), a luminance cap per scene, and quantisation to a bounded palette (the sector's flyover palette under `art/palettes/`, or a median-cut palette of at most 44 colours plus the UI ink for menus), written as indexed PNGs. The runtime adds every moving part procedurally on the same pixel grid (stars, swarm, fleet, bridge frame, holograms, embers, fireworks, glints, wall bezels and lights), so the images stay small and nothing bakes in text or UI.

### Files

| Path | Role |
| --- | --- |
| `art/families/widescreen-backdrops.json` | Style, negative prompt, per-scene layout, prompt, seed, strength, luminance cap, palette or colour count, sector painting and crop |
| `art/workflows/widescreen/img2img-wide.json` | SDXL base + pixel-art-xl img2img: `$init_image` layout, `$prompt`, `$negative_prompt`, KSampler titled `$seed` (denoise via `$node:6.denoise`) |
| `art/workflows/widescreen/txt2img-wide.json` | 1536 × 640 txt2img used while exploring; not part of the shipped run |
| `art/families/widescreen-runs.json` | Generated by `ingest`: workflow, seed, strength, prompts, models and SHA-256 of every raw output in use |
| `assets/images/widescreen/*.png` | Shipping indexed PNGs (`vista`, `hall`, `defeat`, `victory`, `sector-1..5`: 768 × 320; `wall`: 96 × 96 tile) |
| `art/contact/widescreen-contact.png` | Review overview of every finished scene at half size (the wall tiled) |
| `tools/widescreen_assets/` | The driver, Go standard library only (`go.mod`, `main.go`) |

### Rerun

```bash
cd tools/widescreen_assets
go run . layouts                 # seeded img2img inputs -> $WIDESCREEN_WORK/layouts (default /work/tmp/imagegen/widescreen)
go run . jobs                    # the queue -> $WIDESCREEN_WORK/jobs.json
go run . run [--only vista,hall] # GPU: posts each job to $COMFY_URL (default http://studio:8188) and ingests
#   or run each job with studio.run_workflow (workflow, init_image, overrides from jobs.json),
#   save {scene id: output path} as results.json, then:  go run . ingest results.json
go run . process                 # raw cache ($WIDESCREEN_RAW, default ~/.cache/demon-attack/widescreen-raw) -> assets

```

Raw generations stay outside the checkout; `widescreen-runs.json` records their hashes, so the same seed and workflow can be verified, and `process` gives identical bytes for identical raw inputs. Wrap heavy runs in `forge-guard run --` inside the forge.
