# Asset pipelines

How the shipping art is produced and how to regenerate it. Each section owns its own family of assets; research notes on models, licences and consistency techniques live in [asset-pipeline/](asset-pipeline/README.md).

## Backgrounds (flyover with a horizon)

The oblique 3/4 flyover backgrounds (see "Backgrounds: oblique flyover with a
horizon" in [style-guide.md](style-guide.md)) are generated by a reproducible
local ComfyUI pipeline. Every input is committed; the GPU stage is deterministic
for a fixed ComfyUI build, model set and seed (rerunning the mid-ridge strips in
this pass reproduced the shipped atlas byte for byte), and every later stage is
deterministic integer/NumPy work.

### Layout

| Path | Role |
| --- | --- |
| `art/families/flyover-backgrounds.json` | The family spec: per sector the mid-ridge and wall strip prompts, the ground-plane prompt, props, five routes × two landmarks and two creature species; seeds; sizes; luminance and chroma caps; wall width; ground macro modulation. |
| `art/workflows/backgrounds/strip-sheet.json` | Strips (ridges, walls): SDXL base + pixel-art-xl LoRA img2img from a layout sheet (`$init_image`, KSampler `$strength`), an in-graph **roll by half height** (two `ImageCrop` + two `ImageCompositeMasked`) and a masked repaint of the middle band (`$mask`, `SetLatentNoiseMask`), so the result tiles vertically. |
| `art/workflows/backgrounds/ground-tile.json` | Ground plane: the same, then a **second roll by half width** and a repaint of the vertical band (`$mask_v`), so the tile is seamless in x and y. |
| `art/workflows/backgrounds/sprite-transparent.json` | Transparent sprites (landmarks, props, creature poses): SDXL base + pixel-art-xl + LayerDiffuse conv injection; saves RGB (`10_…`) and decoded alpha (`12_…`). |
| `art/workflows/backgrounds/txt2img-pixel.json` | Plain txt2img probe used to tune prompts. |
| `art/palettes/flyover-<sector>.json` | Bounded palettes (43 colours) median-cut from each sector painting. |
| `art/families/flyover-runs.json` | Provenance of every ingested run: workflow, prompt, negative prompt, seeds, strength, models and SHA-256 of each raw output. |
| `tools/flyover_assets.py` | The driver (below). |
| `assets/images/flyover-<sector>.png` | Strip atlas, 384×384: rows mid (ridges) and wall; columns three left variants then their mirrors for the right side. |
| `assets/images/flyover-<sector>-ground.png` | Ground macro tile, 768×768 palette PNG (a 4×4 repeat of the 192-texel seamless tile under smooth periodic light modulation). |
| `assets/images/flyover-props.png` | Shelf-packed props and route landmarks for all sectors. |
| `assets/images/flyover-creatures.png` | One row per species: 8 frames (walk/crawl 0–3, duck 4–5, burrow 6–7) and the same 8 mirrored. |
| `lib/game/flyover_atlas.dart` | Generated metadata: sprite rects, creature rows, layer widths and the per-row edge of every strip. Never edit by hand. |
| `art/contact/flyover-contact.png`, `flyover-landmarks.png` | Contact sheets: every strip (tiled to show the seam), ground crops, sprites and creature frames; and a routes × landmarks grid. |

### Rerunning

```bash
# Keep the venv and raw generations OFF the checkout (the forge's /home/forge/src is a small tmpfs).
python3 -m venv $SCRATCH/asset-venv && $SCRATCH/asset-venv/bin/pip install pillow numpy
PY=$SCRATCH/asset-venv/bin/python
export FLYOVER_RAW=$SCRATCH/flyover-raw   # ingest copies raws here (default .cache/flyover-raw)
$PY tools/flyover_assets.py palettes   # sector palettes from the paintings
$PY tools/flyover_assets.py layouts    # layout sheets + seam masks -> /work/tmp/imagegen/flyover/inputs
$PY tools/flyover_assets.py jobs       # 90 jobs -> /work/tmp/imagegen/flyover/jobs.json
# GPU stage, either:
$PY tools/flyover_assets.py run        # direct ComfyUI HTTP backend (COMFY_URL, default http://studio:8188)
#   (--only strip/,plane/,landmark/krybor limits the jobs; outputs land in /work/tmp/imagegen/flyover/http)
# or run each job through studio.run_workflow with the same workflow, inputs,
# strength and overrides, and save {job id: [output paths]} as results.json.
$PY tools/flyover_assets.py ingest [--results results.json]   # copy raws to $FLYOVER_RAW, record provenance
$PY tools/flyover_assets.py pack       # process + atlases + Dart metadata + contact sheets
flutter test test/flyover_background_test.dart test/sector_background_test.dart test/flyover_perf_test.dart
```

`studio.run_workflow` resolves workflow paths against the project checkout, so
from a worktree pass the worktree-relative path. The HTTP backend binds the same
placeholders (`$prompt`, `$negative_prompt`, `$seed`, `$strength`, `$init_image`,
`$mask`, `$mask_v`, and `$node:<id>.<input>` overrides) the studio tool does.

### Processing stages (`pack`)

1. **Layouts.** Strip sheets hold three 64×192-logical left banks (8 px per
   logical pixel) with a seeded, vertically periodic contour; their interiors
   are textured from the sector painting. Wall layouts are slim (base 15
   texels) and *broken*: seeded bites out of the inner edge and detached
   boulders beyond it. Ground layouts mirror the painting's foreground band;
   the ground job runs at strength 0.95, so the prompt dominates.
2. **Strips.** Box-downscale, un-roll, normalise under the luminance cap and
   snap to the sector palette under the luminance/chroma caps. Ridge alpha keeps
   pixels connected to the outer edge; wall alpha keeps detached boulders and
   drops specks under 6 px. The per-row edge is exported for placement.
3. **Ground.** Box-downscale to 192 texels, un-roll in x and y, tile 4×4,
   multiply by smooth periodic low-frequency light (±40%) so the far plane
   never shows a regular grid, quantise (cap 0.13, chroma 0.22), save as a
   palette PNG.
4. **Sprites.** LayerDiffuse alpha → crop → box downscale to the spec height →
   palette quantise under caps (landmarks 0.40, props 0.34, creatures 0.42 /
   chroma 0.34; saturated warm colours are reserved for hostile fire) →
   binary alpha → despeckle. Creatures get a dark outline whose upper-left
   pixels take a muted light colour (rim light).
5. **Creatures.** One generated pose per species (14–15 texels tall) becomes
   eight discrete frames: four-frame walk/crawl/burrow gait, two duck frames,
   two burrow frames.
6. **Pack.** Strip atlases with mirrored right sides, ground tiles, a sprite
   atlas, a creature atlas with mirrored frames, the Dart metadata and the
   contact sheets. New asset weight is about 1.2 MB (ground tiles ~0.75 MB).

### Runtime contract

`lib/game/flyover_background.dart` uses one camera for everything below the
horizon (y = 172 + 348·z0/z, scale z0/z). Per sector per frame: one baked sky
image, one ground rect with a perspective `ImageShader`, one 110 px fog
gradient, one ridge `drawAtlas` (rotated mid strips), one wall `drawVertices`
mesh, one landmark/prop `drawAtlas` and one creature `drawAtlas`. Strip variants
come from a no-repeat seeded sequence; landmarks, props and creatures are placed
per world segment from stateless seeded hashes, so any flight distance draws
the same picture on every device. Adding a sector or route means adding spec
entries and rerunning the pipeline.

## Sprites

Combat creatures, sentinels, the carrier, the player ship, its cannons, muzzle flashes and every projectile. The contract (layouts, palette, timings, frame selection) is [sprite-atlas.md](sprite-atlas.md); the visual rules are in [style-guide.md](style-guide.md#creature-direction-gargoyles-not-birds).

### Principle

Silhouettes, poses, armour, insignia, weapon mounts and effects are **authored deterministically** in Python on the logical grid, because thirty directional flight frames per damage state, molts, flashes, death sequences and recoil frames must stay aligned pixel for pixel across hundreds of cells. Since the gargoyle round the creatures and sentinels come from `tools/gargoyle_rig.py`, a tiny 3-D rig (volumes, bat-wing membranes, decals) rasterised with a z-buffer and a quantised key light onto the bounded palette: left and right banking frames are real renders of the same anatomy, so asymmetric details stay on their side without mirroring tricks, and wing in-betweens come from joint-angle tables (`FLAP`, `GLIDE`, `COCKED`, `DIVE` in `generate_sprites.py`; `STROKE`, `WARNING`, `CHARGE`, `DIVE`, `RUSH` in `generate_sentinel_sprites.py`). ComfyUI contributes **concept and shading detail only**: gargoyle keyframes are finished onto the grid as a four-level luminance map that nudges the key-light value of hide pixels (stony, leathery texture) before quantisation. AI output never replaces an authored outline, face, insignia or palette, so every frame stays readable at phone size.

### Rerun

A Python venv with Pillow, NumPy and SciPy (`python3 -m venv <dir> && <dir>/bin/pip install pillow numpy scipy`; keep it outside `/home/forge/src`, which is a small shared tmpfs), then:

```bash
python tools/sprite_pipeline.py offline     # finish -> atlases -> sheets; no GPU, byte-identical output (~45 s)
python tools/sprite_pipeline.py all         # keyframes -> edits -> finish -> atlases -> sheets
python tools/sprite_pipeline.py keyframes   # or any single stage: edits, finish, atlases, sheets
flutter test test/gargoyle_review_test.dart && python tools/sprite_pipeline.py screens   # in-engine review sheets
```

GPU stages post the committed workflows to the project's ComfyUI studio over its HTTP API (`$COMFYUI_URL`, default `http://studio:8188`, the same server `studio.run_workflow` drives) with the seeds and prompts above, so the same models and seeds reproduce the candidates; raw outputs go to `$SPRITE_PIPELINE_CACHE` (default `~/.cache/demon-attack/sprite-pipeline`, never the repo). Agents can run the same workflows through `studio.run_workflow` / `studio.queue_workflow` (`$prompt`/`$seed` overrides, `inputs: {input: <keyframe>}` for edits) and drop the outputs into the cache as `<species>-<seed>.png`. `edits` skips molts that already exist under `art/sprites/sources/molts/`; delete them to regenerate. Finishing is CPU-only and deterministic: colour-key matte from the border, largest component, head/torso window (central 34 % of the width, top 80 % of the height), box-sampled onto the hide box `(20, 14)–(44, 52)` of the 64-grid and quantised to four levels at the 20/55/85 % luminance quantiles.

Stages in detail:

1. **keyframes**: four candidates per species at seed, seed+1, … (prompts.json); pick in `selections.json`.
2. **edits**: three molt variants of the selected keyframe (glowing cracks; badly cracked with a chipped horn and torn wings; shattered with a broken horn and shredded wings); used as molt detail maps.
3. **finish**: → `detail/<species>.png` and `detail/<species>-m<k>.png`.
4. **atlases**: `palette.json`, then the four generators. The rig is deterministic (no randomness, fixed tables); Wan2.2 VACE in-betweening and ControlNet pose guidance were considered and not used, because the rig already produces exactly aligned in-betweens and turnarounds for every direction and damage state, and that spares the shared GPU.
5. **sheets**: contact sheets for review.
6. **screens**: composes the in-engine review frames (not part of `offline`; it depends on a Flutter test run).

### Verification

`flutter test` covers atlas sizes, binary alpha, the bounded palette, the gargoyle atlas contract (30 distinct flight frames per damage variant, right banks are not mirrors of left banks, folded upstroke narrower than the level downstroke, every flash, action and elite cell present), the motion state machine (hysteresis without flicker, glide when sinking, longer downstroke when climbing, priority of actions), sentinel pose rules (distinct frames, folding recovery and rush, warnings confined to the creature) and wing-cannon alternation. Visual review uses `test/gargoyle_review_test.dart`'s phone-size renders (every species left / neutral / right in downstroke and upstroke, glides, damage states, elites, combat over each sector background) and the contact sheets above.
