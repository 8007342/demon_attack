# Demon Attack: working rules

Flutter + Flame arcade shooter (an original remake inspired by Imagic's 1982 Demon Attack), a Cloudflare Worker for
scores and review notes, and local asset pipelines (Blender, ComfyUI, radio). Production is
https://demonattack.tlatoani.net. This file and `AGENTS.md` are the only durable home for working rules: nothing
project-related outside the committed repo survives a forge exit. Where this file and a plan doc disagree, this file
wins. Fix it here when a rule changes.

## 1. Branches and pushes

- Flow: `work/<id>` → **squash** into `game` → pull request `game` → `main` (a normal merge commit). Pushes to
  `main` deploy to production, so **never push `main`**. Agents push only their own `work/<id>`. Only the lead
  session squashes into `game`.
  *Why:* `main` deploys, and `game` is where everyone integrates (`.tillandsias/branch-discipline.yaml`, level 1).
- **Generated assets keep no history** (operator, 2026-11-17). Every piece of work lands in `game` as ONE squashed
  commit; intermediate renders and superseded assets live only on the work branch, which is deleted after the
  squash. Never push asset batches straight to `game`. The lead squashes it **from the forge, self-sufficiently**:
  no host session or PR is needed.
  ```sh
  git fetch origin && git switch game && git merge --ff-only origin/game
  git merge --squash origin/work/<id> && git commit   # title "<id>: <summary>", body = the branch's story + trailers
  # gates (§2) on this tree, then:
  git push origin game && git branch -D work/<id>     # local ref only, see below
  ```
  The git mirror's pre-receive hook **refuses ref deletion** ("receive hardening policy"; checked 2026-11-17), so the
  forge can't delete a remote `work/<id>` yet. Record each squashed branch in `plan/handoff-*.md` for cleanup, and
  don't try to work around the refusal.
  If `git merge --squash` conflicts, have the work branch merge `origin/game` and re-push, then squash again. Don't
  resolve generated files by hand (§4).
  - `game` → `main` stays a **normal merge** via PR. `game` is already squashed, and squashing again would make the
    two diverge.
  - When `main` gets commits of its own (licence PRs), bring them into `game` with
    `git merge --squash origin/main`, then gate it and push it like any other squash.
  *Why:* operator, 2026-11-17: the checkout's 3.6 GB disk filled with art history (§9), and "forges should be
  self sufficient", so the forge does not depend on a host coordinator for routine merges.
- **Merge, don't rebase, once a branch has been pushed.** The git mirror rejects non-fast-forward pushes, so a pushed
  work ref is never rewritten. If `game` moved, `git merge origin/game` into your branch. A branch that depends on
  another agent's branch builds on the **pushed** ref (`refs/heads/work/<id>` in `git ls-remote`, which also lists
  `refs/remotes/...` copies), never on a local ref that other worktrees can see.
  *Why:* two agents lost time to rebasing pushed branches (blocker logs A31, B T3b).
- Worktrees live under `~/.cache/tillandsias-project/worktrees/<name>`, never under `/home/forge/src`.
  *Why:* the checkout under `/home/forge/src` is the operator's.
- Stage paths explicitly (`git add <path>…`, never `git add -A` at the root). Never commit `.agents/skills/`
  (forge-managed, regenerated by OpenSpec) or `.claude/`.
- Every commit ends with the `Co-Authored-By:` / `Claude-Session:` trailers your session gives you.
- Never take an outward-facing action (a PR, an issue, a message, a deploy) without asking the operator.
- **Releasing `game` → `main`:** the forge holds no GitHub credentials, by design; never run `gh auth login`. When the
  operator asks for a release, push `game` through the gates, then ask the coordinator session (`macuahuitl-fedora`,
  via SendMessage) to open the `game` → `main` PR from the host with your title and body. Give the operator the PR
  link; they press Merge. Agents never merge to `main`. *Why:* PR #3 (2026-11-17); before that, the forge told the
  operator it couldn't be done. This is a stopgap until forges can open PRs themselves (Tillandsias 2065-ccx9,
  #1123). A regular user has no coordinator session, so don't add new dependencies on one.

## 2. Test gates

Run all of these before any push to `game`. Every command here was run on 2026-11-16 and passed.

```sh
flutter analyze                 # must print "No issues found!"
flock ~/.cache/tillandsias-project/flutter-test.lock flutter test --concurrency=2   # must print "All tests passed!"
npm run test:worker             # node --test test-worker/*.test.mjs: "# fail 0"
npm run build                   # scripts/build-web.sh: the game and /gallery/ web builds
openspec validate <change> --strict
```

- Judge `flutter test` only by the line `All tests passed!` (or `Some tests failed`) at the end. *Why:* a toolchain
  flake once let an untested push through; the exit status of the forge wrapper is not enough.
- **Host memory: `flutter test` runs on the HOST, not in the forge.** On 2026-11-16 five concurrent flutter_tester
  processes reached about 51 GB (the largest 18 GB) and took down the operator's desktop. The rules:
  - Always run tests through the shared lock with a concurrency cap, as above: one suite at a time across all agents.
    `dart_test.yaml` sets `concurrency: 2` as well.
  - `review`-tagged tests (`*_review_test.dart`, the contact-sheet renders) are skipped by default. Run them on
    purpose, one file at a time:
    `flutter test --concurrency=1 --run-skipped --tags review test/<file>_review_test.dart`.
  - Never write an unbounded loop in a test (`while (m.demons.contains(d)) m.hitDemon(d);`). Bound it with a guard:
    a rule change such as an invincible phase turns it into an infinite loop that allocates on every turn.
  - Dispose every `ui.Image` a test creates.
- Run one `flutter` command at a time. A second concurrent `flutter test` can fail with
  `runtime_unavailable: podman failed at step … (timeout)`; retry once, alone. *Why:* the lane's toolchain container is
  shared (blocker logs A25, B T2).
- Wrap heavy local jobs (`npm run build`, ML inference, big image or audio batches) in `forge-guard run -- <cmd>`
  (`tools/forge-guard/README.md`). *Why:* the forge's memory limit is soft; crossing it stalls everything silently.
- `openspec validate --all --strict` does not pass on `game` yet: three main-spec warnings remain (see
  `openspec/changes/guidelines-hardening/design.md`). Your own change must validate strictly.
- Calibration gates run inside `flutter test`; section 7.

## 3. Code conventions

- `lib/game/model.dart` (≈4 600 lines) is the deterministic simulation. Its `part of 'model.dart'` files:
  `life_loss.dart`, `sentinel_rush.dart`, `ground_war.dart`, `ground_war_v4.dart`, `model_bonus.dart`,
  `model_flow.dart`. Rendering is `lib/game/scene.dart`; the page, controls and audio bridge are `lib/main.dart`.
- **The model is pure Dart.** `dart run tools/analyze_difficulty.dart <prefix>` and `tools/profile_difficulty.dart`
  run it headless, without `dart:ui`, so code the model imports must not import `dart:ui` or Flutter. Painters
  live outside its import graph (e.g. `lib/game/bonus/bonus_painters.dart`). *Why:* blocker log B F2.
- Section markers: `// --- <topic or change>` comments mark where a change hooked into shared files; they are the
  index (`grep -rn '^ *// --- ' lib`). Add one when you hook a new change into `model.dart`, `scene.dart` or
  `main.dart`.
- Events: a raw string in `model.events` is forwarded by `GameEventObserver` (`lib/game/game_events.dart`) as a
  `GameEvent` of the same name (except `GameEventNames.unforwarded`: `shot`, `hit`, `explosion`, and `incoming`)
  **and** passed to `audioSfx` in `lib/main.dart`. A structured event queued by the model reaches only the
  `GameEvent` consumers (radio, music). Don't emit both under one name, or the radio speaks twice.
- Formatting: the tree is not `dart format`-clean. Format only the files you changed (`dart format <file>`), never
  `dart format lib`. *Why:* formatting other agents' files creates merge conflicts (blocker log A27).
- Don't refactor shared files (`model.dart`, `scene.dart`, `main.dart`) while other agents are working in them; plan
  the refactor as an OpenSpec task instead.

## 5. Asset pipelines

- **One format per asset; no duplicates.** (operator, 2026-11-17: "No fallback format, this project is already asset
  heavy, no need to duplicate assets. Just keep the latest, unless the older one is signifficantly smaller in size.")
  Ship each asset in a single, current format, with no fallback copies (e.g. no AAC beside Opus) and no committed
  lossless masters. When a newer render or format replaces an asset, delete the old one, unless the older format is
  significantly smaller. The recipe (workflow, seed, pick) is the record.
- **Durability:** host resets wipe `~/.cache` and everything outside the repo. Commit the picked raw renders (e.g.
  `art/sprites/sources/…-selected/`) and the rebuild recipe (family JSON, seeds, commands). *Why:* re-rendering the
  same seeds is **not** byte-identical (GPU nondeterminism); a reset on 2026-11-15 lost pilot raws and venvs.
- **Autonomy:** drive production work to completion yourself, with agents. Make the picks yourself and log each one
  with its reason in the run ledger (`plan/render-runs/`) and on the contact sheet (`art/contact/`). The operator
  overrides later. *Why:* waiting for a pick stalls the pipeline for hours.
- **Rig families** (`tools/rigkit`, Python only because bpy forces it): `PY=$(lua tools/boss_rig/setup_bpy.lua)`
  makes or verifies the bpy 5.3.0 venv (`--check` only checks). Then run `$PY -I tools/rigkit/rig.py FAMILY.json --check`
  (the grammar gate) and `$PY -I tools/rigkit/rig.py FAMILY.json OUT …` (clay, hint, depth, normal, id and z passes),
  then `bake.py` (the projection bake). `lua tools/rigkit/bake_family.lua art/families/<family>.json <hull>` rebuilds
  one hull from its committed picks without a GPU. Family schema: `openspec/changes/boss-hero-assets/design.md` §8.5.
- **Review sheets** (`tools/rigsheet`, Go): build with `cd tools/rigsheet && go build -o
  ~/.cache/tillandsias-project/bin/rigsheet .`. Its commands (`fit`, `maskdiff`, `bakefinish`, `budget`, `views`,
  `stages`, `mock`, `lineup`, `grid`, …) are listed at the top of `tools/rigsheet/main.go`.
- **ComfyUI studio** (host `studio.*` tools): `studio.start {}` when `studio.status {}` says it is down; run committed
  workflows under `art/workflows/` one job at a time; free GPU memory with `gpu.unload_model`. **Never call
  `studio.restart`.** *Why:* it crashed the studio and broke its volume mount on 2026-11-15
  (`plan/render-runs/RESUME.md`).
- **Model downloads need the operator's consent token.** `image.generate` and the studio answer `consent_required`
  with an `ask` sentence. Show it to the operator word for word, and retry only with the token they approve. Never
  start a download on your own.
- **Music and voices are blocked on tillandsias#1103.** Don't work around it, and don't build the missing nodes
  in-forge. Until it lands, new radio lines play a borrowed placeholder clip, or with `"pending": "text"` they show
  their own words and play no audio.
- The asset-pipeline tiers and stages are in `tools/asset_pipeline/README.md`. The production runner
  (`lua tools/production/run.lua <job.lua>`) is in `tools/production/README.md`.

## 6. OpenSpec and plans

- Every piece of work is an OpenSpec change in `openspec/changes/<id>/` (proposal, design, tasks, delta specs).
  `openspec list` shows what is open. `openspec/specs/` is the truth about the shipped game, so archive a change
  once all its tasks are checked: `openspec archive <id> -y`, or `--skip-specs` if its text is already in the main specs.
  Archive changes in the order they were made.
- Keep each requirement's text under 500 characters, because strict validation rejects longer ones. Put detail and
  numbers in scenarios. A MODIFIED block replaces the whole requirement, so copy every scenario you keep.
- Two agents on one change: each owns a capability spec (`specs/<capability>/spec.md`), a named section of
  `design.md`, and its own task group appended at the end of `tasks.md`.
- The `openspec-propose` skill only plans. When a task says "design and implement", write the artifacts by hand in
  the same format.
- Long-running work lives in `plan/`: operator feedback rounds (`plan/operator-feedback-*.md`, newest first), render
  ledgers (`plan/render-runs/`), style guides (`plan/*style-guide*.md`, `docs/styleguide/`), research
  (`plan/*research*.md`, `plan/research-source-ledger.md`).

## 7. Calibration gates

`plan/calibration-current.md` holds the current numbers, and `plan/difficulty-calibration.md` the formulas and their
history. Balance changes must keep these tests green; they run inside `flutter test`:

- `test/difficulty_calibration_test.dart`: the 318-wave defence budgets. Reproduce them with
  `dart run tools/analyze_difficulty.dart <prefix>`.
- `test/campaign_playtest_test.dart`: every campaign completes, and the swarm metrics stay within the accepted bounds.
- `test/boss_endurance_test.dart`: carrier endurance, pooled over the difficulties, within 5 % of its baseline, and
  each difficulty within 10 %.
- `test/perspective_difficulty_test.dart`: the perspective game stays within about ±10 % of the flat game.
- `test/sentinel_rush_fairness_test.dart`: the rush can be escaped.

When a change moves a number on purpose, record the before and after values and the commit in
`plan/calibration-current.md`.

## 8. Provenance

Every research conclusion in a spec or a plan doc keeps its sources next to it: author or organisation, title, URL
or citation, and date read. Use the form `[source: Author/Org, "Title", URL, read YYYY-MM-DD]`. A source counts as
"read" only if its page was actually fetched. A source seen only as a search-result snippet is cited as
`[source: Author/Org, "Title", URL, unread: snippet only]` and does not make the claim sourced. A claim with no
read source is marked `[UNSOURCED: plan/provenance-audit.md#<id>]`. Never invent a citation, and never route around
the forge proxy (for example through host browser tools) to reach a blocked reference site.
*Why:* earlier research kept its conclusions and lost its sources, so nobody could check them (operator, 2026-11-16).
The audit is in `plan/provenance-audit.md`.

## 9. Forge rules

- Tooling language: Lua > Rust > Go. Use Python only when a library forces it (bpy, the existing Pillow and TTS
  pipelines; run them with `python3 -I`). *Why:* Python multiprocessing once stalled the forge's shared memory. The
  forge's Lua has no JSON module, so read JSON with `jq`.
- Stop a process with `pgrep -af <name>` and then `kill <PID>`. Never use `pkill -f` or `killall -r`. *Why:* the
  pattern also matches your own shell's command line and kills it.
- Temp files go in your session scratchpad, not `/tmp` or the checkout.
- **The checkout's disk is small.** In this forge `/home/forge/src` is a 3.6 GB tmpfs. On 2026-11-16 it filled to
  100% (`.git` 1.3 GB, `.dart_tool/flutter_build` 908 MB of stale build hashes), and a git index write and the web
  build failed. Keep it clear:
  - write review renders and other bulky scratch output under `~/.cache/tillandsias-project/`, not the checkout's
    `.cache/`;
  - after a build, prune `.dart_tool/flutter_build` to its two newest directories;
  - run `git repack -d` / `git gc` after art batches;
  - never commit intermediate renders, only the picks and their recipes (§5).

  If final art keeps growing `.git`, propose Git LFS or a separate assets store to the operator. The disk itself is
  tracked as a Tillandsias packet (coordinator, 2026-11-17).
- The forge's bash policy hook refuses a whole compound command if any part of it is refused (e.g. an `rm` whose
  target it cannot resolve). Keep risky steps in their own command.
